## 二、全自动想定工厂（核心修正：消灭一切机械人工动作）

**owner 原话的落地解释**：人在环里的角色从"执行者"变为"评判官"——粘贴脚本、点保存这类机械动作全部自动化；人只在控制台自认为合格后做评判、给反馈。审批安全不依赖人盯每一版，而依赖：自动安检 + 每版哈希留档 + 跑批前哈希校验（追溯链不断）。

### 流水线（每一版候选的生命周期）

```
需求/战法意图（人+OKF）
 → 我生成建场 Lua（用 CMO lua 工具包规则，见第三节）
 → 自动安检（LAB-01 黑名单+差异预览+三件套哈希留档）
 → 自动执行（通道见"关键未知"）
 → 自动保存候选 .scen（scenario.save 工具面）
 → 自动回读核对（装载→比对期望清单→哈希钉死）
 → 自检 QA 门（见下）──不合格→ 我带证据自动返修（≤3 轮，熔断报人）
 → 自认为合格 → 出"人评判卡"（指标摘要+关键事件时间线+与设计意图差异+OKF 依据）
 → 人给反馈 → 我修改 → 再进 QA 门
```

### 自检 QA 门（控制台自己判想定合不合格）——三层判据

| 层 | 判什么 | 怎么判（数据源） |
|---|---|---|
| L1 结构完整 | 该在的都在 | 回读后比对期望清单：双方单位数/类型、任务数、参考点、事件触发器数量；DBID 有效性（F1 `Db3kSearch` 工具复核，`CoreF1AutomationFacade.cs` L794） |
| L2 能跑通 | 不报错、时钟走 | 试跑 N 脉冲：消息日志无 Lua 错误、无异常事件；仿真时钟正常推进；`simulation.status` 正常终态 |
| L3 效果合理 | 像设计的那样打 | 事件 CSV 判据：有 WeaponFired（佯攻波真的发射了）、有探测/交战事件（红方真的反应了）、关键事件时间窗符合战法设计（收网时机）、无一边倒异常（如蓝方首轮全灭=布阵错误） |

三层全过 = "自认为合格"，出人评判卡；任一层不过 = 带证据返修（证据=具体缺失项/错误日志/CSV 缺口），**同一版最多返修 3 轮，不收敛立即熔断报人**（监理准则二）。判据阈值随候选类型登记进 QA 配置，逐步用经验校准（每次校准记 knowledge.md）。

### 关键未知（升级为 D1 第一优先验证，决定全自动是否成立）

全自动链的唯一缺口是**"我从 F1 外编程触发 执行+保存"的通道**。已核实的选项按优先序：

1. **任务库注入（首选）**：助手 TaskOrchestrator + `assistant.db`（SQLite）已在 F1 内自动编排执行工具；若我能向任务库注入任务（写 DB 文件/任务文件），则 `unit.add`/`scenario.save`/`simulation.run` 全自动可达，全程走白名单。**D1 上午 1 小时核实注入点与写门审批策略。**
2. **7777 Lua socket（执行）+ 任务注入（保存）**：建场 Lua 经 7777 最直接（`LuaServerManager.cs` L94），但 Lua 无保存 API，保存仍须选项 1。**7777 默认仍禁用，启用需 owner 书面授权+防火墙限 127.0.0.1**（`LuaSocketClient.cs` L161 有 localhost 客户端先例）。
3. **控制台桥（兜底）**：若 1/2 均不通，由流水线开发最小 C# 桥（localhost 端点→ToolInvocationService，约百行，高风险件送 sol/owner 审）。这是 v1 的微型复活，工作量远小于 v1 全量适配器。

**闭合判据**：D1 内实现"我发一个任务 → F1 自动建一个单位 → 自动保存 → 我回读到该单位"，全程零人工触碰 F1。不闭合 → 启动选项 3 桥开发（不阻塞其他并行任务），同时人工通道（贴面板）保底候选链不中断。
