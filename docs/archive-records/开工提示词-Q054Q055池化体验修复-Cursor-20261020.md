## 二、各件技术要点

### 1. 弹性槽位（本单最大件，先出设计再写码）
- 现状：`POOLING_POOLS_JSON` 写死 2 槽；槽位目录 `D:\soft\F1-slots\slots\slot-XX\`（app+data 两棵树），桥端口 9478 起顺排；supervisor=`LabConsole\tools\pooling\slot_supervisor.py`（start/stop/status 已有）。
- 目标：会话需要绑槽时——有空闲槽用空闲槽；没有且未达上限则**自动 provisioning 新槽并拉起**（找/写 provisioning 逻辑：从模板槽复制目录树、分配端口、注入令牌环境变量）；达上限则按既有排队口径等槽。上限新 env：`POOLING_MAX_SLOTS`（默认 4，非法值启动即抛）。
- 会话租约释放后槽位**保活不销毁**（避免反复 provisioning 的磁盘复制开销）；`POOLING_MAX_SLOTS` 只管并发活槽数。闲置回收（N 分钟无租约自动 stop 进程、保留目录）作为可选项实现，默认关，env 控制。
- 兼容：现有 slot-01/02 目录与 `POOLING_POOLS_JSON` 旧配置必须能无缝被新机制接管（旧配置存在时当作"预置槽清单"）。

### 2. 自动看护
- supervisor 加 watch 模式（或独立 `--watch` 循环）：周期探活各活槽进程+桥端口（探活口径=现有"401 无令牌响应即就绪"），发现进程 gone 自动重拉，写日志；重拉失败连续 3 次则停手并在日志/健康接口标 degraded（防抖动）。
- 注意与 proxy 的关系：看护在 supervisor 侧，proxy 不 fork 子进程。

### 3. 错误码区分
- proxy 调槽桥连接失败（ECONNREFUSED/超时）时，不再透传笼统 upstream 错误；返回结构化错误 `{code:"SLOT_INSTANCE_DOWN", slotId}`，给模型的文案明确："槽位实例未运行，监督器正在重拉，请稍候重试；**不要引导用户重启推演主程序**"。
- 配合 #2：proxy 触发一次 supervisor status 探活（只读），若确实 down 可在文案中带"已请求重拉"。
- /health 的 pooling 段补每槽 alive 状态。

### 4. 保存路径回填（纯 proxy 侧，避免 C# 编译）
- proxy 按槽跟踪"当前想定源路径"：成功的 scenario.load / scenario.save 响应里记录 path（按 manifest 的 pooling.slotId 键控）。
- scenario.save path 缺省/空白时：有跟踪记录→自动填入（**Q-016 确认门流程不变**，确认文案显示将覆盖的正是该文件名）；无记录→维持挂起。
- 重启恢复：proxy 重启后跟踪表为空即回落现状，不强求持久化。

### 5. 告示人话化
- blockedNotice / marked 告示文案改两句式：第一句人话（"AI 刚才声称『已经保存』，但它实际没有执行任何操作，这句话不可信，已被拦截"），第二句给操作员的行动建议（"请让它重新执行，或要求它先执行再汇报"）。
- 技术字段（动词清单）可折叠/小字保留，别删——排查要用。

### 6. 底版同步
- provisioning 新槽时：把公共底版清单（默认=`空白想定.scen`，env/配置文件可扩）从生产树 `D:\soft\F1\F1-测试\Scenarios\AI\` 拷入新槽 `data\Scenarios\AI\`；已存在不覆盖（用户可能在槽内改过）。
- 顺手给现有 slot-01/02 补一次（已拷过，幂等即可）。
