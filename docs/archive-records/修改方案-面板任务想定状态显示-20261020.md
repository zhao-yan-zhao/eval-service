## 2. proxy：runtime-tracker.mjs（新增，约 100 行）

按**槽**记账（想定状态活在槽对应的 F1 实例里，不按会话；槽 0/未池化 = 生产实例，作为默认槽）：

```js
// 状态：Map<slotKey, { slotId, scenarioTitle, scenarioPath, dirty, updatedAt }>
// slotKey = slotId ?? 0（未池化生产实例）
// dirty 三态：true=有未保存修改 / false=与盘一致 / null=未知（proxy 重启后未观察到 load/save）
```

钩子规则（挂在 server.mjs `invokeBridge` 成功返回之后，只认 `r.ok`）：

| 触发 | 动作 |
|---|---|
| `scenario.load` 成功 | `scenarioPath = r.inner.path`，`scenarioTitle = r.inner.summary?.title ?? path 文件名`，`dirty = false` |
| `scenario.save` 成功 | `scenarioPath = r.inner?.path ?? args.path ?? 原值`，`dirty = false` |
| 其他 `spec.mutating === true` 的工具成功（unit.add / event.upsert / doctrine.set / simulation.run / simulation.stop …） | `dirty = true`（simulation.run/stop 也算：推演跑过内存态已偏离盘面） |

`updatedAt` 每次变更刷新为 ISO 时间。

**落盘持久化**（防 proxy 重启丢状态——今天"保存路径全靠猜"的事故就有重启因素）：
- 每次变更原子写 `<panelDataRoot>/runtime/slot-<key>.json`（临时文件+改名，沿用 scenario-handoff.mjs 的 `writeJsonAtomic` 先例）；
- proxy 启动时读回；**读回后 dirty 强制置 null（未知）**——重启期间槽内 F1 可能已被手动改过，proxy 不敢凭重启前的记录声称"已保存"；scenarioTitle/Path 可展示但标注来源时间（updatedAt 字段自带）。

注意保持"重启恢复"语义诚实：**绝不把重启前 dirty=false 的状态恢复成"已保存"**。

## 3. proxy：接口（server.mjs 新增路由）

```
GET /api/conversations/:taskId/:roundId/runtime
→ 200 { slotId, slotAlive, scenarioTitle, scenarioPath, dirty, updatedAt }
```

- `slotId`：优先 `guardSlotOf(sessionId)`；会话失忆时读 manifest `pooling.slotId`（复用 server.mjs:405-413 的恢复逻辑）；都没有 → `null`（未绑定槽，单实例生产场景）。
- `scenarioTitle/scenarioPath/dirty`：从 runtime-tracker 按槽取；无记录 → 全 null，前端显示"尚未装载想定/未知"。
- `slotAlive`：本批恒 `null`（注释注明"待 Q-054 /health pooling 段落地后填充"）。
- 会话不存在 → 404 沿用现有会话接口口径；taskId/roundId 走 `sanitizeId` 消毒（与相邻路由一致）。

为什么不开新顶层路由而挂在 conversations 下：状态与会话强绑定展示、复用现有参数校验与前端调用约定；且并入现有 GET 会话接口会让那个已返回 events 的胖接口更胖，独立轻接口前端可单独高频轮询。

## 4. 前端：useRuntimeStatus.ts（新增 hook，UI 由关定）

仿 `useAlarms.ts` 最小模式：

```ts
// POLL_MS = 10_000；仅当前处于③段会话页时启动轮询，离开即停
// 返回 { slotId, slotAlive, scenarioTitle, scenarioPath, dirty, updatedAt } | null
```

展示建议（仅建议，不作约束）：③段标题栏加一小行/徽章区——
`槽1 · 测试想定v3.scen · ●未保存`（dirty=true 红/橙点；false 灰点"已保存"；null "状态未知"）。
要点：dirty=null（未知）必须有别于"已保存"，防止重启后给人虚假安全感。

## 5. 测试（proxy 侧，全部纯函数/内存态）

新增 `runtime-tracker.test.mjs`，断言表：

1. load 成功 → title/path 落账、dirty=false；
2. load 后 unit.add 成功 → dirty=true；
3. save（空路径覆盖）成功 → dirty=false、path 不变；
4. save（显式 path 另存）成功 → dirty=false、path 更新；
5. 只读工具（scenario.get_summary / db3k.search）成功 → dirty 不变；
6. 失败调用（r.ok=false）→ 状态不变；
7. 落盘→重建实例读回 → title/path 在、dirty=null；
8. GET 路由：绑槽会话返回正确 slotId；未绑槽返回 slotId=null；未知任务 404。

`package.json` 的 test:all 清单**只加不改**既有条目顺序（红线照旧）。

## 6. 边界与不做的事

- 不动桥（C#）、不动 F1 引擎、不动 F1-B/S；
- 不做 SSE 推送（轮询够用，10s 与报警同频，满足"10s 内反映"验收口径）;
- 不替 AI 自动保存；本方案只**显示**落盘状态，保存决策仍在人/AI；
- slotAlive 本批不实现，字段占位；
- 若 Kimi 侧 Q-054/Q-055（按槽想定跟踪表）并发施工——**本方案第 2 节就是那张表**，开工前对一声，谁先做谁占名，避免双份。

## 7. 验收口径（对齐交接单三条）

1. 会话绑槽后 `GET .../runtime` 返回正确 slotId；
2. AI 调 `scenario.load` 成功后 10s 内（前端下个轮询周期）接口反映新 title/path；
3. AI 调 `unit.add` 成功后 dirty=true，调 `scenario.save` 成功后 dirty=false；
4. （附加）proxy 重启后 dirty 呈现"未知"而不是假"已保存"。
