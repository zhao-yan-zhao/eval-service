## 1. 工作流全景图（B 段 v0.1）

```
实验设计文档（A 段产物：docx 给人看 + 机器可读底稿给机器）
  → B1 编译：文档 → 建场规格书（结构化清单：阵营/单位/参考点/任务/
      事件触发器/判据埋点/导出配置/结束条件）——中间契约，全程比对基准
  → B2 翻译：规格书 → 建场脚本（按 CMO lua 工具包规则机械翻译，六铁律）
  → B3 安检：静态检查器（六铁律+黑名单+DBID/坐标规则，LAB-01/13 已闭合）
      → 三件套哈希留档
  → B4 执行：桥装载基座想定（scenario.load，LAB-14/15 已闭合）
      → 建场脚本经审核模板通道执行（关键缺口，见 §7 LAB-B2）

  → B5 回读：get_summary 比对规格书期望清单（单位数/类型/任务数/
      参考点/事件数）→ 哈希钉死
  → B6 试跑判读：simulation.run（有界脉冲）→ 事件 CSV + 想定内埋点
      → 三层判据（结构完整/能跑通/效果合理，QA 门 LAB-07 已闭合）
     ──不合格→ B7 返修（按失败层定修法，同一版 ≤3 轮，熔断带证据报人）
  → B8 蒙卡小批试跑（monte_carlo_runner，M3 已真机验证）：
      验证能自然终局、指标分布稳定、成功率带置信区间
  → 自认为合格 → 出人评判卡（§5）
  → 人反馈（通过/打回+意见/方向调整）→ 修改 → 再进 QA 门
```

源码实读得出的四条结构性结论（设计前提，证据见 §9.8）：
1. **.scen 是二进制序列化容器**——不能像文本一样拼装，唯一合法生成路径是"引擎内构建→scenario.save"，不存在离线拼文件的捷径。
2. **建场 API 面无盲区**——阵营、五型单位、参考点、任务、事件触发器、学说/电磁管控、弹药挂载、气象、判据埋点（键值/计分）、事件导出开关，沙盒里全有对应函数。
3. **桥禁止自由脚本，只放行结构化工具和"审核模板"**——逐个加单位已实跑验证；但任务、事件、判据埋点这类复杂结构必须走"过检脚本作模板注入执行"的通道，这是 B 段对流水的唯一新能力件硬需求。
4. **蒙卡能跑的三个硬条件**——想定能自然终局（必须内置结束条件，否则跑批死循环）、无交互弹窗（无人模式会卡死）、事件导出配置随想定走（否则跑完没数据可判）。这三条进规格书作强制字段。

**owner 钦定建场纪律（2026-09-14，B2 翻译段与 B6 判读的强制规则，全文见 §9.9）：**

1. **分层控制，声明式优先，脚本是最后手段**：可预设的单元直接部署；行动不复杂的用航线（舰船等）；行动稍复杂、数量稍多的用任务控制；任务和航线都难以表达的精细化行为才用触发器+脚本。条令同理：条令能设的用条令，管不了的才用触发器+脚本。数据获取同理：事件输出选项的表能覆盖的就用表，覆盖不了才用触发器+脚本输出。
2. **轻量化**：脚本尽可能少遍历、少循环；触发器尽量不要每秒触发。
3. **性能精简**：传感器越多、非机场设施单元越多跑得越慢，部署尽可能精简；蒙卡想定必须能及时结束（反面教材：大赛某队想定单局蒙卡跑近一个白天）。
4. **结束纪律**：要求不高就用时间触发器直接结束；需要条件满足立即停止且结束时要输出数据的，用触发器+脚本——**脚本内先执行输出代码，再调用想定结束函数**；禁止直接用"想定结束动作"（可能先执行结束动作而跳过输出，导致不输出）。
5. **全局变量初始化**：触发器选"延迟一秒"类，不用"想定加载即触发"类（后者可能导致全局变量加载失败）。

### 4.0 这段流程干什么

你说一段战法想法 → 系统先**挑错**、再**补全**、再**写成固定格式的文档**、最后内部质检。全过，才允许往下走。你全程只做两件事：拍板、挑选。

### 4.1 第一步：挑错（四项体检）

自相矛盾 / 张冠李戴（装备干不了被指派的活）/ 物理做不到 / 违反用户给定约束（只查用户自己给的约束；用户没给的规则不查不提）。每个毛病出问题报告：原话+错在哪+依据+1~3 个改进建议。只报告不擅改；用户坚持原样的标"用户拍板保留"存档。

### 4.2 第二步：补全（缺的信息出选择题，不出填空题）

每个缺口出 3~5 个候选，表格列=方案内容/优势/局限，优势局限必须有 OKF 依据；作战意图类问题不给推荐、必须用户选；全部问题报告+候选合成一份《方案确认书》一次回完。

### 4.3 第三步：写实验设计文档（档案头 + 固定 12 节，Word 交付）

节名：实验目的/实验背景/初始态势/双方编成/变量设置与约束条件（核心，做厚：变量维度清点+实验矩阵+取舍建议；干扰设置单独问用户）/关键假设/实验方案（含量化成功判据）/关键行动（每方≤5条）/推演过程（固定格式时刻表）/推演记录/数据统计/结论（后三节跑完自动回填）。表达规范五条：学术文风、无内部代号、外文名词先中文后括号英文、无内部规则注解、依据标注可读。

### 4.4 依据标注规矩

每个决定至少挂一条可读依据；找不到标"知识缺口"并出登记单（带"是什么/给谁看/三选一"说明）；不许拿一般印象凑数；大赛文件不作依据（除非用户明确参赛）。

### 4.5 第四步：内部质检（11 条，不向用户叙述机制）

战术说得通 3 条、装备真实 3 条、强度有对标 2 条、约束满足 1 条、标注齐全 2 条。全过才交付；不过回修 ≤2 轮，仍不过带证据报人，不卡死（缺口节标暂定可先行）。

### 4.6 两个待 owner 点头的判断

①作战意图类问题只给选项不推荐；②挑错只报告+建议，覆盖权在用户。

```
    判据 | 阈值 | 实际值 | 通过/未过 | 证据位置（可回溯）

    无则按消耗量对比并注明）
五、稳定性（蒙卡小批，如有）：成功率 xx%（置信区间 xx~xx%，n=局数）
六、依据与诚实声明：OKF 依据清单；知识缺口提示；本版 AI 补齐清单
七、请您定夺（三选一）：
    ✅ 通过（归档为正式想定）
    ↩ 打回（选问题类别：战术不合理/装备不对/强度不对/效果不符意图/
       其他，附一句意见）
    ↔ 方向调整（一句话说方向，我重做）
══════════════════════════════════════════════════════════════
```

设计意图：人 30 秒看完能判；每项判定带证据位置可回溯；反馈三选一结构化回收，打回意见按类别路由到对应段落修（战术→A 段文档；装备→规格书；强度→变量设置；效果→QA 判据或 lua）。

## 6. QA 门判定方案（v0.1）

沿用 v2.1 三层框架，L3 判法做一处升级——**双通道判读**：

| 层 | 判什么 | 怎么判 |
|---|---|---|
| 结构完整 | 该在的都在 | 回读比对规格书期望清单：双方单位数/类型、任务数、参考点、事件触发器数；装备编号经数据库复核 |
| 能跑通 | 不报错、时钟走 | 有界脉冲试跑：消息日志无脚本错误、无时钟停滞、正常终态；蒙卡模式下能自然终局 |
| 效果合理 | 像设计的那样打 | **通道一·事件数据（客观事实层）**：武器发射有没有、探测/交战发生没有、关键事件是否落在设计时间窗、战损方向是否符合意图、有无一边倒异常。**通道二·想定内埋点（判定层）**：建场时把成功判据写进想定自身的键值/计分通道（成功率判据埋点方案 CNT-04 已成形），推演结束想定自己报分 |

**为什么双通道而不是只看事件数据（取舍理由）**：事件数据回答"客观上发生了什么"，但判据是想定内生的——"靶舰损毁过半算达成"这种判定，事件数据里没有一个现成字段，每次都要离线重算且容易口径漂移；埋点让想定自己当记分员，判定口径随想定版本一起走、可哈希钉死。事件数据仍是证据底座（埋点判 1 但事件数据里没有任何交战，说明埋点写错了），两者互证。蒙卡跑批后，埋点判定直接聚合成成功率+置信区间（指标工具已有），事件数据支撑归因。

**判据从哪来**：实验设计文档第 7 节的量化成功判据，在 B1 编译时机械翻译成判读配置（事件类判据→事件数据规则；达成类判据→埋点判据）。阈值初值由 A 段文档给定，随跑批经验校准，校准记知识库。

**返修环修法路由（B7）**：结构层失败→修脚本/规格书；能跑层失败→修脚本（运行错误）或规格书（配置错误）；效果层失败→先分"实现错了还是设计错了"（实际事件与文档期望逐条对）：实现错回 B2/B1，设计错回 A 段改实验设计文档（人评判环节打过回票的同理路由）。
