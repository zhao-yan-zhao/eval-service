## 一、owner 原话（痛点）

> "现在回复都是单次回复 如果在等系统跑完 得等用户问才能回复 想办法解决一下"

真机表现（10-21 晚面板会话实录）：AI 起跑短局后说"正在运行，等它跑完我立刻接着读取数据"——然后**就没有然后了**。用户问"跑完了吗？"，AI 凭记忆答"跑完了"，被 claimcheck 三连拦截（"本轮自述动作缺少对应工具证据"）。用户体验=AI 说了会盯但根本没盯，问了还答不上。

## 二、根因（监理已查实，直接给你结论）

1. **会话是请求-应答制**：没有用户回合，模型永远不会开口——这是架构事实，本单就是要补"系统主动发起回合"的通道。
2. **guard 的轮询不是干这个的**：guard.mjs poll() 是起跑后确认"真跑起来了"，MAX_POLLS=15 × 20s ≈ 5 分钟封顶就 stopPolling 解冻（fail-open 防卡死）。两小时的全量局跑完时，**proxy 里没有任何组件知道**。guard 相位机在 status 查询进来时能识别终态（isConfirmed），但前提是"有人来查"。
3. **现有可复用资产**：
   - 报警通道现成：POST /api/alarms/popup（看门狗在用）→ 面板铃铛+数字、③段 AI 下回合被告知、ack 清零。alarms.test.mjs 有测试范式。
   - guard.mjs 有 isConfirmed / isTerminal / 槽相位机 / invokeBridge 全套原语。
   - Q-059 懒拉起后 invokeBridge 遇槽连接失败会自动重拉重试，watcher 轮询不会因为槽重启就瞎报。

## 三、要做什么

**proxy 侧：新增"完局守望者"（run completion watcher）**

1. `simulation.run` 成功（guardOnRunSuccess 之后）→ 为该槽登记一个 watcher：每 30~60s 一次 `simulation.status`（走 invokeBridge，带槽路由），直到出现以下任一终局：
   - **跑完**：isConfirmed / 终态（Succeeded 等）→ 生成"完局通知"
   - **失败**：Failed 等终态 → 生成"失败通知"（带 summary）
   - **槽实例消失**：连续 N 次连接失败且 Q-059 重拉后仍失败 → 生成"实例异常通知"（与 Q-063 崩溃场景联动，用户最痛的就是这个）
2. 通知落地**双通道**：
   - **a. 复用报警通道**：POST 内部等价物 /api/alarms/popup（铃铛+弹窗），文案人话，例：「槽 1 的推演已跑完（场景时钟 2:00:00，共 72000 脉冲）」「槽 1 推演失败：xxx」「槽 1 的推演程序连接中断，看护正在重拉」
   - **b. 新增挂起通知口**：`GET /api/runs/notices?sessionId=xxx` → 返回该会话未消费的完局通知数组；`POST /api/runs/notices/ack` 消费清除。通知里带：slotId、runId、结局（done/failed/down）、实际脉冲数、场景时刻、想定名、时间戳。
3. watcher 生命周期：随槽相位走——guard 相位离开 running/unconfirmed（含 Q-065 自愈复位、slot-reset、stop）→ watcher 撤销；proxy 重启不恢复（ notices 落盘可选，不做也不拦）。
4. 防重：同一 runId 只通知一次；watcher 自身报错只记日志不炸主流程。

**前端侧（最小改动）**：

5. 面板轮询 /api/runs/notices（可与现有 alarms 轮询同节拍同开关）。
6. 有通知时：①顶部横幅/会话内系统卡片「推演已结束，AI 正在读取结果…」；②**自动发起一个续跑回合**——以 system 身份注入：「【系统】槽 X 的推演已结束（结局：xxx，runId：xxx）。请按 skill 读取产物数据并汇报结果。」让模型自己走工具读数、自己汇报——这样 claimcheck 有真工具证据，不会再现"凭记忆答跑完了被三连拦"。
7. 自动续跑回合要防滥用：仅当该会话最近一条助手消息处于"等待推演"语境（可简单判：该会话存在未 ack 通知即触发一次，触发即 ack）；用户正在输入时不打断，等当前回合结束再补。
