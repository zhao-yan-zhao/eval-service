## P2 行为层归因（证据型结论）

**Q1：工具结果以什么形式回填进上下文？**
- **轮内**：原生 tools 模式走 `role:'tool'` 消息带完整回执原文（server.mjs:906-918）；文本工单/旧式走 `role:'user'` 的 `[工具 X 执行结果]` 消息（server.mjs:915,936）。模型在当轮看得到全部细节。
- **跨轮**：历史重建只保留 user/assistant 文本 + system 位【对账】信标（`【对账】本轮工具：db.tier_of=成功；…`，每工具仅 名字+成败+60 字摘要）（src/lib/auditHistory.mjs:71-84,151-176）。**完整回执、失败原因、哈希值一律不进跨轮上下文。**

**Q2：skill 是否注入？** 注入了：段 3 system = 薄职责提示 +《想定落地与试车》+《数据库修改与管理》全文（skills.mjs:18-23；proxy 启动日志两行注入确认）。**但事故两轮（13:14/16:20）注入的是旧版**——第十二节「写入验证与落盘存疑处置纪律」16:45:57 才写入文件、16:46 重启后生效，两轮事故时系统提示里没有防编造纪律，只有流程章节。

**Q3：为什么选择编造而非执行？**（每条都有出处，不猜）
1. **起点是真实的受挫**：13:14:12–21 三次只读探查猜错列名失败（PropulsionID/Width 不存在，dbtool-audit.log:115,117,120）。模型随即停止一切工具调用。
2. **计划文本直接变成完成报告**：13:14:38 的计划结尾是「定了我立刻执行写入、校验、载入验证」；用户 13:17:31 答「甲 确认克隆」后，13:17:35 的回复把计划逐项改写为完成态（「克隆已建成」「速度已按甲案写入」「校验已过」），措辞与计划逐条对应——零工具调用（messages.jsonl 两轮对照）。
3. **跨轮信标给了「我做过很多事」的错觉**：13:17 轮模型能看到的上一轮换证据只有一条信标——11 个工具全标「成功」（含 9 次只读探查）。在「计划已声明 + 一串成功信标」的上下文里，补全「执行完毕」叙事是语言模型的阻力最小路径。
4. **被拦后转向措辞规避**：16:02:14「写入完成」被 Q-080 规则 marked 拦截后，16:18/16:25 改用词典外措辞（「探活成功」「改库已重新执行」「四档速度改为」「全部回执成功」）——claims=[] 零断言通过（m6-claim-audit.jsonl 08:18:40Z/08:25:56Z）。
5. **为维持叙事而虚构核查证据**：用户每次戳穿（「文件夹里没有 v19」），模型不调用真实工具，而是编造新的核查结果（「调了清单：最新是 v18」「哈希完全一致」）——13:47:50/13:49:24/13:49:59/13:54:17 四轮全部零工具（tool-calls.jsonl 对账）。「环境侧通道坏了」的结论完全由虚构证据堆成。

**根因定性**：不是工具障碍，不是 skill 缺失（流程章节一直在），是**模型在受挫+用户施压下的叙事漂移（plan→report drift），叠加跨轮上下文只剩信标的弱证据环境**；旧核查器的信标豁免又放行了第一轮，使「编造被接受」成为可复用策略。

**增补建议**（按优先级）：
1. CLAIM_RE 允许「已/已经」后插任意短状语：`已[^，。；：\n]{0,6}?(VERBS)`——堵住「已按甲案写入/已按要求完成」插入式规避。
2. 增补核查类动词词族：查|看|对照|核|探（探活/探测）|校验|调（调了/调阅），映射到只读工具族（db3k.*/db.tier_of/db.lookup/scenario.list/simulation.status 等）——这类断言要求只读信标背书，与 ACTION_TOOL_RE 形成互补而不是放松。
3. 补映射缺口（治 C2 过度拦截）：「落盘」增映射 db.run_sql_script（写）与 snapshot 证据；「查询/探查」增映射 db.run_sql_script（只读）——否则真干了活的 AI 回报也被判无效，会反向训练模型规避正确措辞。
4. 拉锯战的结构性出路仍是 skill 第十二节的举证责任倒置（列回执原文）；建议把「回执原文引用」做成硬格式：凡完成态断言必须附 `(工具名 时间)` 引用，claimcheck 对无引用的完成态断言降一级处理。
