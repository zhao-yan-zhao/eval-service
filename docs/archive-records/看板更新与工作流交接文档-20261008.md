## 0. 一句话心智模型

**老板不看你干活，老板只看监控台。你写的每一个字段，就是老板看到的全部世界。**

```
老板的眼睛：电脑 http://localhost:7100 ｜ 手机 http://100.86.107.59:7100
                    ▲ 3 秒轮询
        监控服务（常驻计划任务，开机自启，与 Kimi 桌面端无关）
                    ▲ 读文件
        <项目目录>\LabConsole\monitor-state.json   ← 你唯一的对外喉舌
                    ▲ 唯一合法写入方式
        state_writer.py（原子写 + 自动维护时间戳/序号/统计）
```

三条命线，记死：

1. **updatedAt / heartbeatAt 超过 10 分钟不刷新 → 老板手机收到「监控失联」推送**（每 30 分钟重复推一次，直到恢复）。
2. **写入 `kind=review_fail` 或 `kind=escalate` 的事件 → 老板手机立刻收推送**。escalate 等于打电话叫人，别滥用。
3. **老板从监控台发的暂停/恢复命令，90 秒内必须回执**，否则他手机收「控制命令未确认」推送。

## 1. 多项目多面板（2026-09 下旬新增，老文档没有）

### 1.1 机制：一个服务端，同一时刻只激活一个项目

配置文件：`C:\Users\admin\Documents\kimi\workspace\ai-pipeline-monitor\monitor.config.json`

```json
{
  "projectDir": "D:\\soft\\F1-BS\\deduce_code_ui2",     // ← 当前激活项目（服务端全局唯一）
  "allowedRoots": ["D:\\soft\\F1-AI", "D:\\soft\\02-弹道生成工具", "D:\\soft\\F1-BS\\deduce_code_ui2"],
  "projects": [
    { "id": "f1-ai",     "label": "体系推演实验控制台",  "dir": "D:\\soft\\F1-AI" },
    { "id": "ballistic", "label": "02-弹道生成工具",     "dir": "D:\\soft\\02-弹道生成工具" },
    { "id": "f1bs-ui2",  "label": "F1-BS 推演编辑专版UI", "dir": "D:\\soft\\F1-BS\\deduce_code_ui2" }
  ],
  "push": { "wecom": {...}, "appToken": "...", "uid": "..." }
}
```

- 前端顶栏从 `GET /api/config` 拿 `projects[]` 渲染成**项目切换按钮**；点击后前端调 `POST /api/config`（body `{"projectDir": "<dir>"}`），服务端把 projectDir 原子写回配置文件（保留 push/projects 等其他字段），前端随即重拉数据并重置事件高亮。
- **切换是服务端全局的**：所有打开看板的设备看到的是同一个激活项目。不存在"我手机看 A 项目、电脑看 B 项目"。
- `POST /api/config` 的 dir 必须在 `allowedRoots` 白名单内，否则 403。`projects[]` 里的 dir 会在服务启动时自动并入白名单。
- 若配置里没有 `projects[]`，服务端退化为用 `allowedRoots` 生成可点选列表（id=root-0/1…，label=目录 basename）。

### 1.2 切换面板后，服务端读哪些文件（解析顺序固定）

设激活项目目录为 `<dir>`：

| 用途 | 文件 | 解析顺序 |
|---|---|---|
| 看板状态 | monitor-state.json | `<dir>\monitor-state.json` → `<dir>\LabConsole\monitor-state.json`（先找到的生效） |
| 原始日志（/api/logs?name=X） | 任意 .md/.log/.json/.txt（文件名仅限 `[A-Za-z0-9._-]`） | `<dir>\X` → `<dir>\LabConsole\X` |
| 老板留言 | FEEDBACK.md | 固定 `<dir>\LabConsole\FEEDBACK.md`（不存在则自动创建） |
| 暂停/恢复命令 | current-command.json | 固定 `<dir>\LabConsole\commands\current-command.json` |
| 暂停标志 | PAUSE | 固定 `<dir>\PAUSE`（服务端发 pause 时立即创建，resume 时删除） |

**推论：一个项目要拥有自己的面板，最小文件布局是：**

```
<项目根>\
  LabConsole\
    monitor-state.json      ← 必须，面板的数据源
    FEEDBACK.md             ← 可空文件，老板留言会追加进来
    LOG.md                  ← 可选，看板"原始日志"区默认读它
    commands\               ← 可空目录，老板发暂停/恢复时自动创建
    events.jsonl            ← state_writer 自动维护的历史事件留痕
```

### 1.3 大坑一：看门狗只盯「当前激活」的项目

看门狗（60 秒巡检）读的是 `cfg.projectDir` 对应的状态文件和命令文件。**你切到哪个面板，告警就盯哪个项目；没激活的项目失联、打回、升级，一律不推手机。**

- 切到一个停工项目 = 每 30 分钟一条「监控失联」推送（冷却 30 分钟）。**2026-10-08 实况：激活项目是 f1bs-ui2（09-22 后未更新），老板手机从当天 11:04 起每约 31 分钟收一条失联推送，直至 13:48 告警总开关关闭为止。**
- 收工/停线时的正确做法：**关掉告警总开关**（见 §6.1），不必切来切去。

### 1.4 大坑二：state_writer.py 的项目名是硬编码的

`state_writer.py` 第 19 行：`PROJECT_NAME = "体系推演实验控制台"`。它每次写入都会把 `project` 字段刷成这个名字——**给弹道工具/F1-BS 写状态时如果不修正，面板顶部项目名会显示成"体系推演实验控制台"**（两个非 F1-AI 项目当前就是这个错名）。

给其他项目写状态时，每次都必须带：

```bash
--merge "{\"project\":\"02-弹道生成工具\"}"
```

（长期解法是给 state_writer 加 --project-name 参数，未做之前用 --merge 兜底。）

### 1.5 接入一个新项目面板的完整步骤

1. 在 `monitor.config.json` 的 `projects[]` 里加 `{id, label, dir}`（dir 用双反斜杠）。
2. 确认 dir 在 `allowedRoots[]`（不加也会被服务端自动并入，但显式写清楚更好）。
3. 在新项目根建 `LabConsole\` 骨架（monitor-state.json 可不管，首次 state_writer 调用会自动建；FEEDBACK.md 建空文件）。
4. 首次写入：
   ```bash
   python "C:\Users\admin\Documents\kimi\workspace\ai-dev-pipeline\state_writer.py" ^
     --project-dir "<新项目根>" ^
     --merge "{\"project\":\"<项目中文名>\",\"kimi\":{\"state\":\"idle\",\"detail\":\"已接入监控台\"},\"deepseek\":{\"state\":\"idle\"},\"codex\":{\"state\":\"idle\"}}" ^
     --event "{\"actor\":\"kimi\",\"kind\":\"notice\",\"title\":\"<项目名>面板已接入\"}"
   ```
5. 老板在看板顶栏点新项目按钮（或 POST /api/config）切换验收。
6. 改配置不需要重启服务——每次 API 请求都会重新 loadConfig。

## 2. monitor-state.json 字段契约（逐字段）

完整示例（字段顺序无关）：

```json
{
  "updatedAt": "2026-10-08T13:21:58+08:00",
  "heartbeatAt": "2026-10-08T13:21:58+08:00",
  "sequence": 193,
  "writer": "dev-loop",
  "project": "体系推演实验控制台",
  "stats": { "kimi": {"dispatch": 95, "decision": 108}, "deepseek": {"devDone": 37}, "codex": {"reviews": 51} },
  "kimi":     { "state": "dispatching", "detail": "派发 M5-1 批次定义工单" },
  "deepseek": { "state": "running", "running": 1, "waitingReview": 2, "detail": "M5-1 施工中" },
  "codex":    { "state": "idle", "reviewing": 0, "rejectedWaiting": 1, "detail": "LAB-B5 待审" },
  "events":   [ { "time": "13:21", "actor": "kimi", "kind": "dispatch_dev", "title": "派发 M5-1", "detail": "可选" } ]
}
```

| 字段 | 类型 | 语义与纪律 |
|---|---|---|
| `updatedAt` | ISO 字符串（带 +08:00） | 每次写入自动刷。**前端新鲜度与看门狗失联判定的备用时间源** |
| `heartbeatAt` | ISO 字符串 | 每次写入自动刷。**失联判定的首选时间源**。>10 分钟不刷=前端显示"监控失联 N 分钟"+看门狗推手机 |
| `sequence` | 整数 | 写入器自增，你不用管 |
| `writer` | 字符串 | 标识最后写入者（dev-loop / patrol / manual…），自由文本 |
| `project` | 字符串 | **面板顶部显示的项目名**。多项目下必须用 --merge 显式写对（见 §1.4） |
| `stats` | 对象 | **全量累计计数，单调递增永不清零**。写入器按事件 kind 自动 +1（见 §3.2），不许手工改 |
| `kimi.state` | 枚举字符串 | 见 §2.1 取值表 |
| `kimi.detail` | 字符串 | **一句话人话**，原样上屏。别贴堆栈、别超过两句 |
| `deepseek.state/running/waitingReview` | | running=在跑的 aider 线程数；waitingReview=已交付待审件数 |
| `codex.state/reviewing/rejectedWaiting` | | reviewing=在审件数；rejectedWaiting=打回待返修件数 |
| `events` | 数组 | 追加式事件流，写入器自动截断到**最近 20 条**（旧文档写 50 是错的，以代码 MAX_EVENTS=20 为准） |
| 其他顶层字段 | 任意 | 前端容忍多余字段（如 `LAB-10: {state, detail}` 任务灯、`stage/status/note`）。可以放，但别依赖它们被渲染 |

### 2.1 state 取值表（这组值有中文标签和灯色，别自造）

**kimi（统筹泳道）**：

| 值 | 面板显示 | 灯色 | 什么时候用 |
|---|---|---|---|
| `dispatching` | 派发任务中 | 紫·亮 | 正在派单/送审 |
| `deciding` | 决策中 | 紫·亮 | 正在追因/裁决/拆任务 |
| `running` | 运行中 | 紫·亮 | 在干别的实活（代审/真机验证） |
| `waiting_dev` | 等待 DeepSeek 开发结果 | 紫·呼吸 | 派完了等交付 |
| `waiting_review` | 等待 Codex 审查结果 | 紫·呼吸 | 送审了等结论 |
| `idle` | 空闲 | 灰 | 没有真实在跑线程（收班熄灯，见 §5） |
| `paused` | 已暂停 | 灰 | 收到 pause 命令/PAUSE 文件存在 |
| `blocked` | 等待人工裁决 | 红 | 熔断/需要老板拍板（通常伴随 escalate 事件） |

**deepseek / codex（执行泳道）**：只有三个值——`running`（运行中·亮）、`idle`（空闲·灰）、`error`（异常待处理·红）。

### 2.2 事件 kind 表（决定泳道、配色、是否推手机、是否计 stats）

| kind | 面板文案 | 推老板手机？ | stats 自动累计 |
|---|---|---|---|
| `dispatch_dev` | 派发开发 | 否 | kimi.dispatch +1 |
| `dispatch_review` | 派发审理 | 否 | kimi.dispatch +1 |
| `decision` | 决策 | 否 | kimi.decision +1 |
| `dev_done` | 开发完成 | 否 | deepseek.devDone +1 |
| `review_pass` | 审理通过 | 否 | codex.reviews +1 |
| `review_fail` | 不通过 | **是** | codex.reviews +1 |
| `escalate` | 升级人工 | **是** | 不计 |
| `notice` | 通知 | 否 | 不计 |

- `actor` 只能是 `kimi` / `deepseek` / `codex`，决定事件落在哪条泳道。
- `title` 必填、一句话；`detail` 可选，可以写长一点（面板可展开）。
- 自造 kind（如 `milestone`）能显示但无配色标签、不计数——尽量用上表内的。

### 2.3 前端新鲜度分级（老板看到的"实时性"标签）

| 距 heartbeatAt/updatedAt | 面板显示 |
|---|---|
| ≤2 分钟 | 实时数据（绿） |
| 2–10 分钟 | 数据滞后 N 分钟（黄） |
| >10 分钟 | 监控失联 N 分钟（红） |
| /api/state 拉取失败 | 数据源异常（红） |
| 读到内置示例 | 示例数据·等待接入（黄）——**看到这行说明你的状态文件根本没被读到** |

## 3. 唯一合法写入通道：state_writer.py

### 3.1 为什么必须用它

1. **原子写**（先写 .tmp 再 os.replace）——监控服务 3 秒轮询，手写半截 JSON 会被服务端判 `state_file_unreadable`，前端退回示例数据，看门狗报"数据源异常"。
2. 自动维护 updatedAt/heartbeatAt（+08:00 ISO）、sequence 自增、stats 按 kind 累计。
3. 同步追加 `events.jsonl` 历史留痕（可追溯）。
4. 文件损坏时自愈：损坏原件改名 `.corrupt-HHmmss` 留档后重建，不连环失败。

**禁止**：任何执行器/任何人用 echo、编辑器、手写脚本直接改 monitor-state.json。

### 3.2 命令格式

```bash
python "C:\Users\admin\Documents\kimi\workspace\ai-dev-pipeline\state_writer.py" \
  --project-dir "<项目根目录，默认 D:\soft\F1-AI>" \
  --merge '{"kimi":{"state":"dispatching","detail":"派发 M5-1"}}' \
  --event '{"actor":"kimi","kind":"dispatch_dev","title":"派发 M5-1 批次定义","detail":"工单 workorders/M5-1.md"}'
```

- `--project-dir`：**写到哪个项目的 `LabConsole\monitor-state.json` 就看它**，多项目时代每次必传，不许吃默认值。
- `--merge`：顶层深合并，可多次字段一次给；也可以 `--merge @update.json` 从文件读。
- `--event`：可重复多次，一次调用追加多条事件。
- Windows cmd 里 JSON 双引号要转义（`\"`）；Git Bash 里单引号原样包裹即可。**JSON 里不许出现未转义的换行和反斜杠路径**（路径用 `/` 或 `\\`）。
- 多项目时代每次调用建议带上 `--merge '{"project":"<本项目中文名>"}'` 修正项目名（§1.4）。

### 3.3 八种典型场景的复制即用模板

> 以下以 F1-AI 项目为例；其他项目改 `--project-dir` 和 `project` 名。Git Bash 语法。

**① 派开发单（DeepSeek 开工）**

```bash
  --merge '{"kimi":{"state":"dispatching","detail":"派发 LAB-C1 给 DeepSeek"},"deepseek":{"state":"running","running":1,"detail":"LAB-C1 施工中"}}' \

```

**② 送审理（Codex 开工）**

**③ 开发交付（DeepSeek 报完工，你还没验收）**

**④ 审理通过**


**⑤ 审理打回（注意：会推老板手机）**


**⑥ 决策/裁决（不发任务也想留痕时）**
```bash

```

**⑦ 升级人工（等于给老板打电话，确认真需要再用）**


**⑧ 普通通知/见证（零成本留痕，不推手机）**
```bash
  --event '{"actor":"kimi","kind":"notice","title":"蒙卡批跑 6/6 PASS 归档","detail":"runs/mc-20261008/，QA 0 error"}'
```

## 4. 什么时候刷：动作级刷新时刻表

**总原则（老板原话）：每有个动作就要刷新一次，不许攒到轮末。**

| 时机 | 必做动作 |
|---|---|
| 派单/送审点火后 | **立刻**刷 running（防止下一轮次重复派单） |
| 测试出结果 | 刷一条 notice/dev_done |
| 审理出结论 | 刷 review_pass/review_fail |
| 合并/收编 | 刷 notice + 对应泳道 state |
| 熔断/掐断重派 | 刷 decision + detail 写原因 |
| 老板留言消化完 | 刷 notice 回执（老板能看到闭环） |
| 一轮结束 | 最后刷一次：熄灯（无真实在跑方写 idle）+ LOG.md 追加 |

**收班熄灯（老板硬规则）**：灯只反映真实在跑——aider/codex 没有线程在跑就写 idle；你这一轮没点火任何新线程，kimi.state 也写 idle。「流程活着」不靠灯表达，靠心跳表达。

**心跳分工**：「监控心跳保活」自动化任务每 10 分钟只刷 updatedAt/heartbeatAt 两个字段（纯 Python、零额度）。但它**只在 Kimi 桌面端运行时执行**——Kimi 关了心跳就停，看门狗（独立计划任务，永远在跑）10 分钟后就会推「监控失联」。这是设计如此的"真失联"告警：Kimi 都关了，流水线确实死了。**例外：如果你主动停线收班，提前把面板切到也在停工的项目没意义——三个项目都停时，告警照推，老板知情即可，或由老板决定临时停看门狗计划任务。**

## 5. 老板的干预通道（每轮开工必查，优先级高于一切计划）

| 通道 | 文件（相对激活项目根） | 协议 |
|---|---|---|
| 留言 | `LabConsole\FEEDBACK.md` | 老板从监控台"远程干预"框提交，格式 `## 远程干预（时间，来自手机监控台）`。你逐条消化或转派，处理后在条目下标注「已消化·时间+结论」，并刷一条 notice 事件回执 |

## 6. 告警机制全景（看门狗，server/watchdog.mjs）

60 秒一轮巡检**当前激活项目**，四类告警，推送通道优先级：企业微信群机器人 → 企业微信自建应用 → WxPusher（前一个成功就不再试后面的）：

| 告警 | 触发条件 | 冷却 |
|---|---|---|
| 数据源异常 | 状态文件不存在/读不出/JSON 解析失败 | 30 分钟 |
| 监控失联 | heartbeatAt（或 updatedAt）超 10 分钟未更新 | 30 分钟 |
| 审理不通过 / 升级人工 | 事件流出现新 review_fail / escalate | 每条事件独立 30 分钟 |
| 控制命令未确认 | pending/acknowledged 超 90 秒 | 每条命令独立 30 分钟 |

- 推送失败只记 5 分钟短冷却（网络抖动不会把告警永久吞掉）。
- 看门狗日志：`server\watchdog.log`（每条推送/失败都落盘，可对账）。
- 首轮回避：服务重启后第一轮巡检不对存量旧事件告警（防止开机轰炸）。

### 6.1 告警总开关（2026-10-08 新增）

老板不用监控时可以**手动一键关停全部手机推送**，不用动计划任务：

- **看板顶栏开关**：「告警推送 开/关」（在"开发循环运行中"开关左边），手机网页同样可点。
- **配置文件**：`monitor.config.json` 顶层 `alertsEnabled`（缺省/缺字段 = 开；`false` = 关）。
- **API**：`POST /api/config`，body `{"alertsEnabled": false}`；`GET /api/config` 返回里带 `alertsEnabled`。
- **生效原理**：看门狗每轮巡检都重读配置文件，**60 秒内生效，无需重启服务**。关闭期间告警只写 watchdog.log 不推送、不记冷却——重新打开后如有异常会立即补推一条。
- 关闭的是**推送**，不是巡检本身：看板网页、状态文件、命令通道全部照常工作。
- 注意：重启服务必须连子进程树一起杀（`taskkill //PID <run.mjs的PID> //T //F`），只 `schtasks /End` 会留下持端口的孤儿进程，新实例端口被占会安静退出，造成"改了代码没生效"的假象（2026-10-08 实证）。
