# 问题与解决记录：对比实验·地狱景观·无OKF组（2026-10-12）

> 范围：从建场环境准备到 R1 基线想定 v3 终版的全过程。每条：现象 → 原因 → 解决办法 → 状态。
> 知识库精简条目对应：knowledge.md K159–K170。状态分为 ✅已解决 / 🔶绕路解决 / ❌未解决（已规避）。

## 一、环境与基础设施

### 1. F1 程序与资源根分离，新机迁移后起不来 🔶
- **现象**：把 `WritableRoot.txt` 从 `D:\ZXY\soft\F1\F1` 改指 `D:\F1-AI\F1-测试` 后 F1 无法启动。
- **原因**：F1.exe（D:\F1-AI\F1）与资源根（数据库/想定/配置/授权）是分离的；F1-测试 树资源不完整（疑似缺授权或资源文件）。
- **解决**：按 owner 从原机器发来的方案，还原指向 ZXY 整树；想定、导出、配置全部在 ZXY 树下做，成品复制回 D:\F1-AI 归档。改动前留 `WritableRoot.txt.bak-20261012`。
- **遗留**：资源根长期留在 ZXY 树，双树并存需手工归档（绕路但稳定）。

### 2. 锚点想定绑定的数据库缺失，加载弹窗卡死 ✅
- **现象**：旧锚点 `测试.scen` 绑定 HACM_Modified.db3（本机没有），加载即弹窗，无人值守跑批被卡死。
- **解决**：在 `<资源根>\DB\SwitchDBFileWhenError.txt` 写入 `DB3K_505.db3`，启动时弹窗点「是」换库，另存新锚点 `锚点-测试-505.scen`（绑定 505，免弹窗）。两树 DB3K_505.db3 已核 SHA1 一致。

### 3. F1 禁多开 + 端口归属排查 ✅
- **现象**：曾出现双 F1 实例互踩，桥 9477 行为异常。
- **解决**：`netsh http show servicestate view=session` 查 9477 归属 PID → `taskkill //F //PID <pid>`（git-bash 里必须双斜杠，单斜杠被吞成选项）。

### 4. 长推后不重启 F1，下一局 sim_failed 🔶
- **现象**：两次实证（v2 首试、v3 枚举器局）——上一局全量跑完不重启 F1，下一局 `sim_failed` 于 pulse 0；杀进程重启后同一想定立即跑通。
- **原因**：F1 内部状态残留（未深入定位）。
- **解决**：纪律化——**每局长推后、下一局前必须重启 F1**；基线内存 ~2.4GB 属正常，不要误判为泄漏。

### 5. 桥启动偶发失败 🔶
- **现象**：一次重启后 F1 进程在（~2.1GB）但 9477 始终拒绝连接。
- **解决**：再杀重启即愈。桥就绪判据 = 无 token 请求返回 **401**；403 = 工具不允许；启动后需轮询等待 10–25 秒。

### 6. 中文参数经 git-bash/curl 必坏 ✅
- **现象**：中文想定名/单位名经 bash curl 传桥，报 `invalid_json` 或乱码。
- **解决**：一律写 Python 脚本文件（utf-8）调 `POST /invoke`，不在 bash 命令行里塞中文 JSON。

### 7. 导出配置与落盘 ✅
- **现象**：导出项 GUI 模式不认 ini（K02 已录）。
- **解决**：`Config\EventExportExtra.ini` 已修好（CSV/UnitPos/WeaponFired/UnitDestroyed/Damage/WeaponImpact/WeaponEndgame 全开，Interval=10）；导出落盘 `EventExport\ai\<桥实例>\<run_id>\<想定名>\EventExport_CSV\`，判读全走磁盘 CSV。

## 二、桥接口（代码层面）

### 8. unit.add 参数形态三连坑 ✅
- `dbid` 必须传 **int**（字符串报错）；
- `course` 是**航点对象数组** `[{"lat":..,"lon":..},..]`，扁平数字数组报 `course_waypoint_not_object`；
- 返回的 `ResultJson` 是字符串，需二次 `json.loads`；`speed` 参数不被接受（航速由航线驱动）。

### 9. referencepoint.add 直连 403 ✅
- 参考点必须走模板通道：`template.execute` + template_id `panel.referencepoint.add` + 登记 digest。桥的允许工具集是白名单，不在名单里的工具一律 403。

### 10. strike 任务不派兵死锁 ✅
- **现象**：蓝方打击单元配 strike 任务后全局无动作——strike 只打**已探测到**的接触，无接触时单元原地待命永不进场。
- **解决**：要进场用 **patrol**（会进场，遇接触即交战）；strike 只用于"接触出现后待命齐射"（发射连正是此用法）。

### 11. 桥无删改单位接口，矩阵变体走花名册 🔶
- `unit.remove/delete/set/update/teleport/list` 全部 403。
- **解决**：锚点预置矩阵**最大编制**（6 发射连 + 24 艇），各局用 `mission.create_or_update` 的花名册控制参战数（实证返回 `units_assigned=N`，未挂任务单位全程原地不动）；数量按发射连 15 枚/连取整（U24→30=2 连、U96→90=6 连，已向 owner 声明）。

### 12. 新模板登记摘要本地不可复现 🔶（设计如此）
- **现象**：仿写模板登记进 manifest，`template.execute` 报 `template_registration_digest_mismatch`；对现有模板穷举各种哈希配方（id/文件哈希/时间戳全排列、文件字节组合、JSON 变体）均不匹配。
- **结论**：`registration_sha256` 含 owner 侧审批信息，**审批链真实有效**，这不是故障是设计。
- **解决**：需要新 Lua 能力时走 owner——GUI 改锚点（WRA/事件随锚点继承到所有派生想定）或 owner 用原机器登记工具审批。

### 13. .scen 正文是私有压缩格式 ❌（已规避）
- `Scenario_Compressed` 段非 gzip/zlib/raw-deflate，逆向不值当；放弃手工编辑想定 XML 的路线。

## 三、Lua 事件（代码层面）

### 14. 事件不勾「可重复」只触发一次 ✅
- owner 首版事件没勾可重复，日志只有一对行。必须：可重复 ✓ + 周期时间触发器（5 秒）。

### 15. 本构建 Lua API 与 CMO 不一致 ✅
- **枚举法**：事件动作里 `for k,v in pairs(_G)` 用 io 落盘全量函数名（`lua-api-dump.txt`）。
- 结论：无 `ScenEdit_GetUnits`（复数）/`ScenEdit_ApplyDamage`/`Tool_Distance`；有 `ScenEdit_GetUnit`（单数）/`SetUnitDamage`/`KillUnit`/`Tool_Range`/`SetDoctrineWRA`/`GetDoctrineWRA` 等 100+ 函数。
- 单位枚举替代：建场时单位名全定死，脚本硬编码名表 + `Shahed-136 #N` 编号探测逐个 `GetUnit(pcall)`。

### 16. Lua 里中文按字节处理 ✅
- `string.sub` 切中文船名必错；用 `string.find(s, '自杀无人艇', 1, true)` 纯字节查找。

### 17. 沙箱吞异常 ✅（模板批注实证）
- 注册函数内部抛错会被沙箱吞掉、返回 nil、pcall 捕不到——凡写操作必须**读回验证**（参考点模板即此模式）。

### 18. SetUnitDamage 假成功 + 脚本截断原生链 ✅（重要教训）
- **现象**：近距命中事件全部逻辑跑通（5 秒周期、名表取单位、0.1 海里判定、`KillUnit` 成功），但 `SetUnitDamage` 两种签名都返回 true+table 却**零实际伤害**；同时 `KillUnit` 在 0.1 海里处提前杀死攻击方，把引擎原生撞爆/命中链（艇 280DP、机 72DP 含组件损毁/火灾/进水）整个截断——**有事件版红方零损失，删事件版 3 舰沉/重创**。
- **解决**：owner 拍板方案 A=删除事件，判定全交引擎原生链。
- **教训**：兜底脚本若不能完美复刻原生结算，宁可不要；凡脚本类干预必须做「有/无脚本」对照跑再采信。

## 四、想定设计与仿真领域

### 19. 艇群自杀"失效"的真凶是几何 ✅
- R1 病：12 艇 4 艘巡逻游荡 5 节不到位。根因：**原地打转的编队让艇失去拦截解算**。v2 改红方行驶进场后 12/12 全部接触起爆。当初怀疑的"自杀机制坏了"是误诊。

### 20. 红方走走停停的真凶是航路终点压岛 ✅
- v2/v3 早期红编队 T+13~70 整体停航约 50 分钟。根因：航线终点 118.45E 对部分南侧舰船落在金门岛上，寻路卡死。终点改 118.55E（全水面）后，UnitPositions 逐舰核验 11/12 全程 18–20 节连续航行（其余 3 艘低速段均为战损瘫船，非航路问题）。

### 21. 无人机/艇到达不同步 ✅
- 发射连在厦门（84 km）太远，无人机 T+53 才发射、到达比艇晚。发射连前移金门（62 km，飞行 ~19 分钟）+ 艇线东移 118.70E（冲刺段 30 km）后，两波到达窗口叠在 T+67–79 同区间。

### 22. WRA 按武器型号逐型生效，显示 0 ≠ 已设置 ✅
- 三轮实证：首轮设了 SM-6/ESSM/SM-1，SM-2 IIIA/IIIB 漏（照样打 72 枚）；次轮 SM-2 补设后 SM-1 漏（95 枚——之前无人机到不了佩里射程没暴露）；第三轮全型归零。
- 另：WRA 对话框默认显示 0 不代表已生效（新锚点未设时实测打 87 枚）；**验证口径 = WeaponFired 按弹种计数归零**，不看界面。
- 本实验红方 WRA 清单（5 型）：SM-6 Blk IA、SM-2MR Blk IIIA、SM-2MR Blk IIIB、SM-1MR Blk VI、ESSM。

### 23. 库内替身与声明 ✅（偏差已声明）
- LUCAS 库内无条目 → Shahed-136（条目 4142，发射平台设施 3665，15 枚/连）；**非美国条目**、战斗部改装未实施（不改库）。
- T38 库内无武器 → Generic Suicide USV（4468，200kg 装药，40 节无冲刺）。
- 发射连全弹发射（60≠计划 48），数量按 15 枚/连取整。

### 24. 单局方差不小 → 矩阵必须重复 ✅
- v2 艇 12/12 vs v3 终版 9/12；诱饵舰被击沉与否两版不一致。第④阶段每局位 3 次重复取分布。

### 25. 探测驱动时序 ✅（认知）
- 无人机 strike 发射由探测触发（红方雷达开机→蓝方 ESM 探测 T+47~53）；艇巡逻冲锋由自身雷达探测触发。时序推算必须以探测时刻为锚，不是以 T+0 为锚。

### 26. 沟通/协作层面：GUI 里看的是哪个文件 ✅
- owner 曾在 GUI 里看旧锚点（发射连还在厦门岸边）误以为"问题都没改"。教训：交付 GUI 操作时写明**确切文件名 + 肉眼可辨的地标特征**（发射连在金门岛上、艇线位置），并给可验证的硬指标。
