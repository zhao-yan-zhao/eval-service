## 〇、摘要（先说结论）

1. **并发边界一句话**：proxy 请求级天然并行，但"推演"和"改库"两个全局单槽状态机卡死所有客户端；桥/F1 侧无会话概念，所有状态（想定、时钟、单位、库绑定、推演 job）都是**进程级全局单例**，两条串行链（进程锁 → F1 单 UI 线程）把所有请求最终收口到一处。
2. **推荐**：**第一期 = 方案 C（第二台机，零代码，明天可用）+ 方案 A（proxy 软并行，约 4 人日，周末上线）+ 方案 B 同机双开实测探针（2–4 小时，决策依据）**；第二期（演示后）视探针结果决定是否上方案 B 多实例池。
3. **理由内核**：演示现场是单机演示（100 实体想定、一个人操作），**现场不需要同机并行**；并行痛点在三人开发测试期——C 当天解渴，A 把现有纪律从"人管"变"机器管"且不碰桥/F1/引擎、不进编译窗口，B 有 4 个未确证项（7777/7778/6899 端口、许可计数、SQLite 行为、内存翻倍），演示前上池风险不可控。

## 二、现状并发边界（带证据）

### 2.1 面板后台 proxy（7177）

**会话状态**：无会话概念。请求身份只来自请求体 `{stage, messages}`，无 session id/token/用户标识（`demo-ui\proxy\server.mjs:368-370`；全目录无 cookie/session 用法，唯一 header 用途是 CORS 放行 localhost，`server.mjs:54-64,330`）。**proxy 无状态、多客户端在请求级天然并行**：Node 原生 http 异步并发，无队列无锁（`server.mjs:329,423`），每请求独立 chatLoop 生成器与上游 fetch（`server.mjs:378-398,249-319`）。

**与桥的连接**：无共享连接。每次调用现建 fetch + 60s 超时（`bridge.mjs:14,60-69`），令牌每次现读文件（`bridge.mjs:18-24,51`）。**两个客户端同时请求 = 两条并发 HTTP POST 到 9477，proxy 不做任何排序/串行化**。

**两个全局单槽状态机（多客户端的主要冲突点）**：

1. **推演护栏（guard.mjs）**——"推演进行中禁止查询"纪律的物理实现：
   - 模块级单例 `state = { phase: 'idle', ... }`（`guard.mjs:23-29`），所有客户端共享一份；
   - `phase==='running'` 时**所有客户端的全部工具**（除 simulation.stop/recover）被冻结拒绝，不进桥（`guard.mjs:36-40` + 调用点 `server.mjs:137-138`）；
   - `simulation.run` 乐观置位在同一事件循环内原子（`server.mjs:140→230→231` 检查与置位间无 await），双客户端同时 run 不会双跑，后到者被 `guardPreRun` 拒（`guard.mjs:43-47`）；
   - 每 20s 经 `simulation.status` 轮询自动解冻（`guard.mjs:59-105`），5 分钟超时 fail-open；
   - **副作用**：A 起跑 → B 全部工具冻结；B 的 stop/recover 作用于全局（能停掉 A 的推演）。
2. **改库确认门（dbgate.mjs）**——全局单槽，跨客户端会"串味"：
   - `state = { phase:'idle', plan:null, ... }` 单例（`dbgate.mjs:20-25`）；
   - B 的 present_plan **无条件覆写** A 已呈现/已确认的方案（`dbgate.mjs:70-77` 无 phase 前置检查）；
   - confirm/authorize 只看全局 phase（`dbgate.mjs:84-115`），两客户端交错时存在"B 的请求触发 A 方案的写库授权"风险。

### 2.2 接口程序/桥（9477，F1 进程内）

**单端口单监听器，多客户端连接并行受理，但工具执行串行**：

- 单 HttpListener、单前缀、只绑回环：`AiAssistant.F1Core\Bridge\AiAssistantBridge.cs:22`（`DefaultPort=9477`）、`:108-111`（注释红线"绝对只绑回环地址"）；端口可被环境变量覆盖：`AiAssistantBridge.cs:518-535`（`F1_AI_BRIDGE_PORT`，1..65535 校验），令牌取 `F1_AI_BRIDGE_TOKEN`（`:510`），启动器只注入令牌未设端口（`start-F1-with-bridge.bat:3-4`）。
- 并发模型：单 accept 线程 + **每连接一个 ThreadPool 工作项**（`AiAssistantBridge.cs:148-201`，注释明言"process each connection independently so a hung /invoke cannot block the accept loop and starve /health"）→ HTTP 层并行，/health 永不被 /invoke 拖死（K105/BF-02 已部署实证）。
- **串行点 1——进程级总闸**：全部工具调用过一把锁 `_gate.RunExclusive(() => InvokeCore(request))`（`AiAssistant\Tools\ToolInvocationService.cs:114-117`，锁体 `ScenarioLockService.cs:10-27`）；simulation Run/Stop/Status 临界区同锁（`Simulation\CoreSimulationGateway.cs:101,236,308,369,552`）→ 两客户端并发 /invoke 在工具执行段**排队阻塞在 lock 上，无队列长度、无超时**。
- **串行点 2——F1 单 UI 线程**：桥所有引擎访问经 `RunOnUi`（BeginInvoke+WaitOne，超时 10s）封送到唯一 F1 UI 线程（`AiAssistantBridge.cs:24-25,375-392`；脉冲引擎 5s 超时 `Simulation\CorePulseEngine.cs:432-447`）。
- **无会话概念，全是进程级单例**：当前想定 = 静态字段（`Command_Core\ClientCore.cs:101,425`）；桥会话号写死 `"bridge-session"`（`AiAssistantBridge.cs:545-546`），每桥进程一个合成任务号——**两个客户端 = 同一个 bridge-session 的两次调用**。
- **拒绝而非排队**：mutating 请求在任务运行态直接 `scene_lock_busy` 拒绝（`AiAssistantBridge.cs:329-334`、`ScenarioLockService.cs:200-210`）；仿真运行中拒 scenario.load（`ToolInvocationService.cs:339-345`）；run 重复 job 拒绝（`CoreSimulationGateway.cs:152-157`）；任务控制 `SemaphoreSlim(1,1)` 单活动任务（`ProductionTaskCoordinator.cs:52,209-221`）。
- **"推演中禁止查询"桥内没有实现**：只读路径直接 Dispatch 无 busy 检查（`ToolInvocationService.cs:182-207`、`AiAssistantBridge.cs:277-289`）；该纪律只存在于 proxy 护栏（§2.1）与文档红线（`迁移部署…md:96`、`M7方案…md:53`）。运行时效果：查询封送同一 UI 线程，排在脉冲批次（每批 ≤2s，`CoreSimulationGateway.cs:467-506`）后面自然等待；批次间隙插队实际时序**未确证，需实测**。
- 幂等重放：同 idempotency_key 并发重试等待原请求结果并重放，内存缓存 128 条（`AiAssistantBridge.cs:27,45-47,248-273,429-439`），跨进程/跨重启不共享。
- **桥↔F1 无 IPC**：桥编在 F1.dll 内、随 F1.exe 进程内启动（`F1-AllInOne.csproj:64-76`；`MainForm.cs:40534-40569,40562` → `AiAssistantCompositionRoot.cs:647-674`），引擎调用 = UI 线程封送后直调 `ClientCore` 静态 API。**"多桥"=多 F1 实例，桥不能独立于 F1 运行。**

### 2.3 推演程序 F1

**"单实例"是运维约定，不是程序强制**：`Command\My\MyApplication.cs:576` `base.IsSingleInstance = false;`（VB 框架单实例保护显式关闭）；旧"杀死相同名称、启动时间不同的进程"整块代码已注释（`MyApplication.cs:410-434`）；`NumberOfInstancesRunning` 字段零使用（`GameGeneral.cs:405,729` 残留）。单实例靠纪律维持（`LabConsole\knowledge.md:477` K61：多开→assistant.db 锁竞争+桥端口冲突；`需求记录…:22,26`：同机双开需实测）。

**想定载入 = 进程级全局唯一对象的整体替换**：
- `ClientCore.cs:101,425`：`private static Scenario _CurrentScenario_value;` / `public static Scenario CurrentScenario`；
- 载入清掉：当前方/选中单位/引用/通知/窗口状态（`ClientCore.cs:1322-1421` SetCurrentScenario → `_CurrentSide=null`、`ReleaseReferences()`、`GameGeneral.DestroyPreviousScenario(ref theOldScen, true)`）；**第二个想定加载会把第一个顶掉**（需求记录:14 的代码根源）；

**推演时钟 = 想定对象属性 → 进程全局**：`scenario.set_time` 在全局 `CurrentScenario` 上跑 `ScenEdit_SetStartTime`，只拨开始时间与时长、不复活已毁单位、不改当前仿真位置（`LuaSetTimeTemplate.cs:50-70`、`CoreF1AutomationFacade.cs:762-787`）；所有工具经 `RequireScenario()`（`CoreF1AutomationFacade.cs:966-967`）取同一个全局对象。

**装备库绑定 = 进程内存注册表 + 想定文件载荷指纹**：
- 引擎启动时扫描 `DB\` 目录建"指纹→库"注册表（`DBOps.cs:163-235,783,824-832`），**新库出生必须重启 F1 才进注册表**（`DBOps.cs:568`）；
- 载入想定时按标签/指纹重绑定：`Scenario.cs:2627-2632`（M7-W1 标签预绑定）→ `:2706`（`ResolveScenarioDBBinding` 标签优先、指纹回退、不一致写警告日志）→ `:2708`（标签清空）；
- `DBUsed` setter 相等不重建连接：`Scenario.cs:933-953`（值变化才置空 `_DBConnection` 并重建缓存）；
- **桥载入（scenario.load）把库绑定回退到源库，只有 UI 手动切库能改绑定**（`迁移部署…md:100`；切库清偏好 `DBOps.cs:595-598`）；桥无切库通道（`skills\数据库修改与管理\参考-想定数据库绑定机理与操作规程.md:37`）。
- 绑定状态与进程同生命周期，**同一 F1 实例上两个会话对库绑定的需求无法调和**（会话 A 要库 A、会话 B 要库 B → 必有一个错）。

**核心线程是唯一的、且可被长推不可逆捕获**：桥/脉冲引擎一切引擎访问封送到 F1 单 UI 线程（§2.2）；长推或首射时核心线程被捕获后**不可逆**（K105/K111），只能重启 F1——因此"长推一局一重启"是现行纪律（`knowledge.md:783-787`；`skills\想定落地与试车\SKILL.md:122`）。**这决定了即使同机多开，每个实例的推演吞吐也受"一局一重启"约束。**

**单推演 job 硬约束**：仿真网关单实例、拒绝第二套（`ProductionSimulationMount.cs:24-33`）；run 重复 job 拒绝（`CoreSimulationGateway.cs:152-157`）。

**资源与启动**：单实例约 2GB 级内存（`需求记录…:22`）；F1-Console.exe 是无头跑批（带 `-R/-LUASERVERPORT/-TCP` 参数，`F1_Console\MyConsoleApplication.cs:49-59,412-555`），**不含 AI 桥**（桥只在 GUI MainForm.Load 创建，`MainForm.cs:40534-40569`）；`F1Config\*.ini` 无桥通道配置，桥参数只来自环境变量。

**许可**：浮动许可服务 net.tcp `localhost:2202/F1`，许可参数含 `ConcurrentMaxUser/CountUserPerMachine/CountUserPerAppInstance`（`许可注册\FloatingLicenseService\FloatingLicenseManager.cs:12-22,47-60`）——**许可机制层面具备"每应用实例计数"能力，是否在当前许可载荷中启用未确证**；数据根内含两份机器码绑定 .license 文件；迁移手册未覆盖新机许可转移流程（**未确证，需实测**）。

- **唯一排队点**：所有桥查询被塞进 F1 UI 线程串行执行（`CoreF1AutomationFacade.cs:914-918` RunOnUi）——多 proxy 会话的 db3k.search 在桥内天然串行，但互不阻塞（SQLite 多读者共享）。

**写——写者直连文件，不经桥 HTTP**：

- runner 每步一事务 + 读回断言 + `integrity_check`（`dbscript-runner.py:45-135`）；连接**无 busy_timeout、无 WAL 设置**（`:123`）。
- **两个写者并发**：SQLite 文件锁，默认约 5s busy → `database is locked` → 该步回滚、整体 RUNNER_FAIL（`dbscript-runner.py:93-98`；2026-10-09 `dbtool-audit.log` 有两次 RUNNER_FAIL 实样）；proxy 侧更危险的是**秒级时间戳命名导致同秒任务目录/快照互相覆盖**（§2.1 表 #4/#5）。
- **F1 运行中被外部改写注册库 → FileSystemWatcher 侦测 → 弹窗并可退出程序**（`DBOps.cs:667-707`）——"只改副本库、官方库/在用库禁直改"纪律的根源（`dbtool.py:354-367` guard-check exit4）。
- **多机共享**：数据库和想定都是单写者文件，两台机器不许同时跑同一共享盘数据根（`迁移部署…md:119`）；库获取=文件复制（`DBOps.cs:648-650` 缺库报错"联系作者获取副本"）。

## 三、三个候选方案

> 说明：本方案的 A/B/C 编号按本工单定义。与 `需求记录-控制台并行想定-20261009.md` 路线的关系：本方案 A ≈ 需求记录路线 B（作业队列）＋C（会话锁）的组合升级；本方案 B ≈ 需求记录路线 A（多实例多桥）；本方案 C 是新增的零代码兜底（分工文档第三节已立项"零改动兜底"）。

### 3.1 方案 A：软并行（①②④段并行，③段排队串行）

**原理**：把 proxy 现有的"全局冻结"升级为"**F1 作业租约**"——③段作业（建想定/跑推演/读结果/批跑）按会话排队独占；①②④段非桥工具（对话、文档读写、离线统计）永远并行；桥只读查询在推演运行期仍冻结（守红线），非运行期并行。

**改动范围**：
- `demo-ui\proxy\guard.mjs`：全局 freeze 拆为"租约持有者检查"；新增 FIFO 租约队列（租约工具集合 = bridge mutating 全类：scenario.load/save/set_time、unit.*、mission.*、doctrine.*、event.*、referencepoint.add、template.execute 变异模板、simulation.run/stop/recover、result.read、批跑脚本调用；判定建议按工具的 mutating 属性而非写死名单——白名单随构建漂移有前科 K121）；
- `demo-ui\proxy\server.mjs:137-142,230-235`：执行路径接入租约；排队位置回传给面板；run 的乐观置位原子性保持；
- `demo-ui\proxy\dbgate.mjs`：改库确认门纳入租约串行（消灭 §2.1 的 B 覆写 A 方案问题）；
- 面板（`demo-ui\src\components\ChatFlow.tsx / StagePanel.tsx`）：排队位置提示（"前面有 N 个作业"）；stop/recover 权限收窄为仅租约持有者；
- **桥/F1/引擎：零改动**（桥已有 scene_lock_busy 拒绝语义，排队在 proxy 完成，拒绝不可见）。

**工作量粗估**：proxy 2–3 人日 + 面板 1 人日 + 联调回归 1 人日 ≈ **4–5 人日**（不占编译窗口；依赖 P0-2 死锁修复同批完成，见 §5）。

**风险**：低。核心风险是租约释放与失败路径的完备性（P0-2 修复是前置）；白名单漂移用 mutating 属性判定规避。

**对演示的适配度**：满足"一个人跑推演时，其他人能聊①②段、查文档、做设计"；**不满足两人同时③段**。演示现场单机单操作员场景下完全够用。

**与现行纪律的兼容性**：天然兼容且**机器化**了现有纪律——"单实例单想定单批跑、别人跑批时不许进场"（`skills\想定落地与试车\SKILL.md:66`）从人管变队列管；"推演中禁桥查询"红线**完整保留**（运行期桥工具仍冻结）。

### 3.2 方案 B：多实例池（同机，每会话独占一个 F1 实例）

**原理**：同机跑 2–3 个 F1 实例（各带独立数据根副本 + 独立桥端口），proxy 按"作业槽位"把每个会话路由到固定实例，池管理实例生命周期（启动/租用/回收/重启）。

**改动范围**：
- F1 部署侧：两份 F1 程序目录（各带自己的 `WritableRoot.txt` 指向两份数据根副本）；桥端口用 `F1_AI_BRIDGE_PORT` 错开（机制已存在 `AiAssistantBridge.cs:518-535`）；每实例独立 assistant.db/日志/EventExport（数据根分离自然隔离，§2.2 表 #4-#7）；
- **前置实测**：同机双开探针（见 §5.1 B0 验收）——验证 7777/7778/6899 第二实例绑定失败是否致命（`LoadScenario.cs:860-864`、`LuaServerManager.cs:94-109` 异常被吞）、许可是否按 `CountUserPerAppInstance` 拦截（`FloatingLicenseManager.cs:47-60`）、内存/CPU 是否可承受（单实例 ~2GB）；
- 若探针发现端口必须错开而引擎无参数化（GUI 无 `-LUASERVERPORT` 类开关，Console 才有）：改引擎端口配置 = 进编译窗口（与 P0-1 对地打击、M7 W1W3 攒批）；
- proxy：作业槽位路由（chat→实例端口映射）、每槽位独立 guard 状态（现 `guard.mjs:23-29` 全局单例需改为 Map）、池管理器（实例启动/回收/重启脚本，落实"一局一重启"纪律机器化）；
- 面板：槽位选择/占用 UI（与关同志的任务管理界面合并设计）。

**工作量粗估**：双开实测 0.5–1 人日；数据根/程序目录复制模板脚本 0.5 人日；proxy 槽位+池管理 3–4 人日；面板槽位 UI 1–2 人日；回归 1 人日 ≈ **6–9 人日**（不含引擎端口参数化；若需则 +1–2 人日并占编译窗口）。

**风险**：**高**。四个未确证项（7777/7778/6899 静默失败后果、许可实例计数、SQLite 同根行为、内存 2GB×N）全在演示前无法快速闭环；桥会话号/审计无实例维度（`AiAssistantBridge.cs:545-546`）需小改桥代码；"一局一重启"纪律在池化后必须机器化，否则池形同虚设。

**对演示的适配度**：最好——三人可同时③段。但演示现场是单机单操作员，**现场用不到这个能力**；它是开发期效率方案。

**与纪律兼容性**：每实例内部仍维持全部单实例纪律（禁查询、一局一重启、库绑定人工切库）；新增"槽位绑定"纪律（会话与实例的对应关系不许漂移）。

### 3.3 方案 C：多机分工

**原理**：第二台电脑按迁移手册部署完整环境（手册已备 `迁移部署-F1-AI到新机-20261010.md`，点火五步 + 路径改写六处清单齐全）；软件层只做"会话不串味"的最小改动——proxy 桥地址/工作区路径环境变量化，两台机器各跑各的。

**改动范围**：
- 部署：数据根整目录拷贝（几个 GB）+ `WritableRoot.txt`、start bat、`EventExportExtra.ini`、proxy 工作区路径、LabConsole 脚本路径改写（手册 :66-75 六处清单）+ 逐层点火验证（手册 :77-83 五步）；
- 软件最小改动（0.5 人日）：`bridge.mjs:14` 的 `BRIDGE_URL` 与 proxy 内硬编码工作区路径改环境变量（`server.mjs`/`stats.mjs`/`run_detached.py:8,13-15` 的 `D:\soft\F1-AI` 绝对路径）；
- **新机许可转移：迁移手册未覆盖（未确证）**——部署前必须先实测新机能否注册/运行（`许可注册\` 机器码绑定 .license 佐证风险）。

**工作量粗估**：部署 0.5–1 人日 + 软件配置化 0.5 人日 ≈ **1–1.5 人日**。

**风险**：低–中。唯一实质风险是**新机许可**（未确证）；首次部署有未知坑（手册今天刚出，未实战验证过）。

**对演示的适配度**：开发测试期并行完全解决（两台机器=两个独立环境，互不干扰）；**演示现场若是单机，此方案对现场无帮助**——但现场本来也不需要并行。

**与纪律兼容性**：完全兼容——每台机器维持单实例全套纪律，唯一新增纪律是"两台机器各用各的本地数据根副本，不许共享盘同根"（手册 :119 已写明）。

## 四、推荐与理由

**推荐：一期 = C + A 双轨 + B 双开实测探针；二期（演示后）按探针结果决定 B 池化或 C 常态化。**

理由（结合"演示只剩 1–2 周"）：

1. **约束对齐**：分工文档已定调——"零改动兜底（第二台机，明天能用）"和"程序改造（两天内出方案评审、随即开工，单周内上线）"两条腿同时走（`分工与计划…md:35-43`）。本方案正是把这两条腿落成有验收标准的实施路径。
2. **现场不需要同机并行**：演示目标 = 客户到场单机测试 ~100 实体想定（`分工与计划…md:3-4`）。现场是一台机器、一个操作员——同机并行（B）是开发期效率方案，不是演示需求。演示前把 B 的高风险铺开不划算。
3. **C 当天解渴、风险最低**：迁移手册今天刚备好，部署路径、改写清单、点火顺序、新机 AI 纪律全部成文（`迁移部署…md`），与三台机器单实例纪律完全兼容。唯一未确证项（新机许可）先做 30 分钟级验证即可排除。
4. **A 是单机内能做到的全部**：并行瓶颈的代码事实是"桥/F1 无会话概念 + 想定/时钟/库绑定全局唯一"（§2.2/§2.3）——**单实例下③段物理上无法并行**；A 把能并行的（①②④ + 非桥工具）全放开，把不能并行的（③段）从"人管纪律"变成"机器排队"，且全部改动在 proxy/面板，不碰桥/F1/引擎、不进编译窗口（编译窗口已被 P0-1 对地打击 + M7 W1W3 占据，`问题分析…md:103-108`）。
5. **B 是终态，但不是本周**：4 个未确证项（§2.2 #15、§2.3 许可、§2.4 SQLite、内存）任何一个翻车都意味着池化推倒重来；演示前正确姿势是**先花 2–4 小时做同机双开实测探针**（这也是需求记录 :26 自己定的前置："需先做 F1 同机双开可行性实测"），结果进二期决策。
6. **两条腿互为兜底**：C 若因许可受阻 → A 兜底（单机软并行）；A 若发现必须改桥 → 与 P0-1 攒批进编译窗口；B 实测失败 → C+A 就是长期架构（"多机 + 每机软并行"）；B 实测成功 → 二期上池，A 的租约队列代码直接复用为池的每槽位队列。

### 5.2 第二期（演示后）

- **探针通过 → B 池化**：数据根/程序目录复制模板脚本 → proxy 槽位路由 + 每槽 guard → 面板槽位 UI（并入关同志任务管理界面）→ 池生命周期管理（"一局一重启"机器化：实例长推后自动重启回收）。

### 5.3 验收标准（逐条可测）

**一期——方案 C**：
- [C1] 新机按手册五步点火：`start-F1-with-bridge.bat` 拉起后 45s 内 `http://127.0.0.1:9477/invoke` 无令牌返 401；proxy `http://127.0.0.1:7177/health` 返 `{"ok":true,"hasKey":true}`；面板发一句大白话任务走通（手册 :77-83 原样）。
- [C2] 两台机器**同时**各跑一个完整③段全流程（load→建模→run→result.read→qa_gate），两台 bridge-audit.log 各自记录、零交叉；本机 F1 不受新机影响（tasklist/audit 双查）。
- [C3] 新机许可验证结论成文：能启动、能载入想定、能跑推演（若被拒，立即回退单机 A 路线并报 owner）。

**一期——方案 A（同一台机）**：
- [A1] 两个浏览器窗口同时开面板，各聊①段：双方 AI 回复各自完整、互不串（`m6-claim-audit.jsonl` 两行各自 tools/claims 独立）。
- [A2] 窗口 A 持有租约建想定/推演期间，窗口 B 的①②段对话、文档读写、离线统计全程可用，**零冻结文案**（当前行为是全冻结，这是 A 的核心增量）。
- [A3] 窗口 B 在 A 推演期间发起③段 → 返回**排队位置**（如"前面有 1 个作业"）而非冻结拒绝；A 终态后 B 自动接续；B 的想定与 A 的想定零串味（bridge-audit 对照：B 的 unit.add 全部落在 B 自己的 run 段）。
- [A4] 窗口 B 在 A 推演期间发起桥查询（db3k.search）→ 仍被冻结（**红线保持**），文案明确"推演进行中"。
- [A5] A 的推演 Failed → 租约自动释放（P0-2 修复生效），队列头自动接续，全程无重启。
- [A6] 两人同机同时改库 → 第二人收到排队/占用提示；无同秒任务目录/快照覆盖（对照 §2.1 表 #4/#5 的碰撞场景复现为零）。
- [A7] 回归：固定考题组四段全流程一遍通过，与原单客户端行为无退化。

**一期——方案 B 探针（决策输入，不是上线项）**：
- [B0] 同机双开实测报告成文，逐项给结论：①第二实例设 `F1_AI_BRIDGE_PORT=9478` + 独立数据根（两份 F1 目录）后，两个桥是否都在听（两个端口 /health 分别 401）；②两个实例各自 scenario.load/unit.add/simulation.run/status 全绿（各自想定互不顶替）；③7777/7778/6899 第二实例绑定失败的表现与后果（日志查证，是否影响推演功能）；④许可是否拦截（弹窗/启动失败）；⑤内存实测（任务管理器）与 2GB×N 估算对照。**结论只有两种：可池化（附证据）或不可池化（附阻断项）**——作为二期决策的唯二输入。

**二期（演示后，按探针结果二选一）**：
- 池化路线：[B1] 三人同时各占一槽跑全流程，audit 证明三槽零串味；[B2] 实例长推后自动重启回收，"一局一重启"零人工；[B3] 槽位绑定不漂移（会话重连后仍回原槽）。
- 多机路线：[C4] 第二台（甚至第三台）机复制部署 ≤ 半天；[C5] 审计文件按会话/槽位维度可追溯；[C6] CLI 旁路通道与面板通道在同一台机上遵守同一队列纪律（桥侧排队或 LabConsole 脚本门禁二选一落地）。
