## 1. 生产事实核对（先 grep 再引用）

### 1.1 工具 schema（模型可见）

出处：`ToolRegistry.CreateDefaultV1()`（`CMO-netcore-src/AiAssistant/Tools/ToolRegistry.cs`）。

与本单直接相关的字段（逐字）：

- `scenario.get_summary`：必填 `scope`∈`all|units|missions|events`，`max_items` 1–200  
- `unit.status`：必填 `max_items`；可选 `unit_id` / `side` / `cursor`（稳定分页）  
- `unit.add`：必填 `side,dbname,lat,lon`；可选 `name,dbid,unit_type∈Aircraft|Ship,loadout_id,course[]`；**Ship 必须带 `dbid`**（Core `LuaUnitAddTemplate` 缺 `dbid` 直接拒）  
- `unit.update_position`：必填 `unit_id,lat,lon`  
- `event.upsert`：必填 `event_name,enabled`；属性含 `description`、`trigger_type`∈`time`、`trigger_minutes` 1–100000、`actions` 数组  
- `scenario.save`：空对象  
- `simulation.run`：必填 `duration_pulses`；可选 `speed`∈`1x|2x|5x|max`  
- `result.read`：必填 `run_id`；可选 `aggregation`、`max_rows`

### 1.2 系统提示词纪律（影响提示词写法）

出处：`ProductionTaskSystemPrompt.Text`。

关键约束（设计必须迎合，否则模型会按纪律少调工具）：

- 参数必须符合 schema；`unit.add` 仅 Aircraft/Ship；Facility 不可用  
- 仿真后系统会注入 `[系统观察 result.read]`；之后最多再补 1 次 `result.read`，然后必须中文总结收尾  
- 跑仿真前应用 `scenario.get_summary` 读 `game_resolution`，再算 `duration_pulses = 目标秒数 ÷ game_resolution`  
- **任务目标明确时，禁止无关侦察**（含 `unit.status` / `db3k.search`），除非用户任务**明文授权**  
- 未要求仿真时禁止 `simulation.run`

因此：本单提示词必须**明文授权** `scenario.get_summary`、`unit.status`、`db3k.search`（若走检索舰船）、以及双轮判定所需工具。

### 1.3 轮次语义（A5 / A13）

出处：`LimitPriority` + `LoopParameterSettings` + 设置面板「最大轮次」。

- 默认：`max_rounds=5`，`same_error_limit=3`（当前 WritableRoot `ai_settings.loop_parameters` 只读可见仍为该 JSON）  
- **`round_no` 在认领新的 `simulation.run` 时消耗**；`SimClaim` 阶段若 `round_no >= max_rounds` → `Failed(round_limit)`  
- 用户文案：`UserFacingErrorCatalog` →「任务轮次已用完，已自动停止」  
- 限轮汇报模板：`LimitReportTemplate`（含 `task_id` / `round_no` / 终止状态 / `error_code`）  
- UI：`AiAssistantSettingsPanel` 控件「最大轮次」`_numMaxRounds`（1–20）

**含义：**

- A5 要观察「第二轮仿真」→ 设置保持默认 ≥2，且 journal 里应出现 **两次** `simulation.run`  
- A13 要观察上限停 → 必须另设 `MaxRounds=1`，且任务文案仍要求「不满足就要再跑」；第一轮后第二次 `simulation.run` 应被保险丝拦住并中文汇报

### 1.4 `event.upsert` 白名单（A14）

出处：`LuaEventTemplate` / InMemory 镜像校验。

- 触发器：仅 `trigger_type=time`  
- 动作仅三：`send_message` / `set_doctrine` / `activate_mission`  
- `send_message` 必填：`type,side,message`  
- 事件 `IsRepeatable=false`（模板写死）  
- **无**自由 Lua / script / shell 工具面

**编码事实（必须写进 Owner 脚本，避免假失败）：**

- 工具字段名叫 `trigger_minutes`，但 Core 模板把该整数直接写入 CMO `Time` 槽；CMO 按 `DateTime.FromBinary(long)` 解读（见 `EventTrigger_Time.FromXML`）。

- 本编排把 A14 观察点定为：**事件已创建 + 跑仿真后出现 SpecialMessage**；**不**把「精确等满 N 分钟」写成硬通过条件。若要坚持相对分钟精度 → 见 §6 待决。

### 3.1 为何 A5 不与 A13 合测

- A5 通过条件需要 **第二次** `simulation.run` 成功认领并完成  
- A13 通过条件需要第二次 `simulation.run` 在 `MaxRounds=1` 时被 `round_limit` **拒绝**并汇报  
- 同一任务上「必须成功第二轮」与「必须打中上限」互斥 → 分两单

### 3.2 A5「第一轮不满足→第二轮」如何尽量可重复

**机制（不靠模型自由发挥目标）：**

1. 明文规定第一轮**必须**把舰加在点 A（固定经纬度）  
2. **成功标准**却要求 `unit.status` 读回位置落在点 B 的小方框（与 A 明显分离）  
3. 第一轮结束后，若未落入 B 框，只允许 `unit.update_position` 到 B，再 `scenario.save` → 再 `simulation.run` → 再读 → 中文汇报  
4. Cursor 事后硬门：journal/`ai_task_steps` 中 `simulation.run` **≥2**，且两轮之间出现 `unit.update_position`（或等价改坐标成功工具步）

**为何第一轮高概率不满足：** A 与 B 纬度相差 0.20°（约 22 km 量级），短仿真（约 2 分钟）即使舰在动，也几乎不可能从 A「漂」进 B 的 ±0.01° 框；且提示词禁止第一轮直接放到 B。

**残留风险：** 真模型若违令第一轮就放到 B，则只会出现一轮仿真 → A5 记 **待确认/重跑**，不得假报通过。替代方案见 §6。

```sql
-- A8：基线备份路径与哈希
SELECT backup_id, kind, source_path, backup_path, file_hash, file_size_bytes, created_at_utc
FROM ai_backups
WHERE task_id = '<TASK_ID>'
ORDER BY created_at_utc;

-- A4/A5/A14：工具步序列（看 simulation.run 次数、event.upsert、update_position）

       substr(request_summary,1,180) AS req,
       substr(response_summary,1,180) AS resp,
       prev_hash, entry_hash, chain_version
FROM ai_task_steps
WHERE task_id = '<TASK_ID>'
ORDER BY sequence_no;

-- A7：journal 工具轨迹（勿把整库消息 dump 进公开聊天）
SELECT sequence_no, role, name, substr(content,1,120) AS content_head,
       substr(tool_calls_json,1,200) AS tools_head, created_at_utc
FROM ai_task_model_journal
WHERE task_id = '<TASK_ID>'
ORDER BY sequence_no;
```

`state` 对照：`7=Completed`，`8=Failed`，`9=Cancelled`，`10=TimedOut`。
