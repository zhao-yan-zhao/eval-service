## 3. 要讨论透的两个问题

### 问题 A：构想 → 靠谱的文本想定

用户输入可能是几句话的口头构想（"红方用诱饵群消耗蓝方防空，无人艇侧翼突击"），也可能是半结构化描述。要设计：

- **理解与澄清流程**：什么信息必须追问、什么可以用 OKF 默认补齐、补了哪些必须向人声明？
- **文本想定的固定结构**：模板长什么样（作战背景/双方编成/意图与战法/关键事件脚本/成功判据/约束条件）？模板本身要不要从大赛规则（OKF 里有）反推？
- **OKF 引用规范**：每个设计决策必须挂 OKF 依据（案例编号/规则条款），怎么标注、缺口怎么报？
- **靠谱判据**：什么叫"靠谱"？（战术上说得通、装备映射真实存在、强度校准有战例对标、规则约束不违反）每条判据如何落地成检查项？

### 问题 B：文本想定 → 合格的 .scen（全自动，owner 最担心）

owner 实测过：cursor 能生成完整 lua，他手动粘贴进 lua 控制台执行、保存成想定，能跑。**但有了控制台之后，粘贴和保存不允许再有人参与，必须全自动**——这是控制台存在的意义。要设计：

- **工作流的分段与每段出入口**：构想 → 文本想定 → 建场 lua → 安检 → 执行 → 保存 .scen → 回读核对 → QA 门 → 人评判卡。每段的输入/输出物、合格判据、失败后的返修路径。
- **QA 门怎么判**：owner 提过用事件输出选项输出的 CSV 判断是否达到期望效果——CSV 里哪些指标对应"想定成立"（接触产生了没有、交战发生了没有、关键事件脚本触发没有、双方战损是否符合意图方向）？"或者其他更高明的方式"——你负责想透并给推荐。
- **不合格返修环**：修谁（改 lua？改文本想定？改构想理解？）、修几轮熔断、证据怎么留？
- **人评判卡格式**：控制台自认为合格后报给人的那张卡，要有哪些字段人才看得懂、判得快？人的反馈怎么结构化回收（通过/打回+意见/方向性调整）？

### 问题 C：怎么固化成 skill（元问题）

- **粒度**：一个总 skill 还是一串小 skill（如：构想澄清 skill / 文本想定生成 skill / 建场 lua 生成 skill / QA 门判定 skill / 评判卡生成 skill）？各自的触发条件和输入输出。
- **skill 怎么生成与进化**：第一版谁写、写完怎么验证、跑起来后卡点知识（如何解决的、路如何走通的）怎么回流进 skill 与知识库——owner 明确要求"重复的坑不要踩两次"。
- **与流水线的接口**：skill 文件放哪、谁维护、开发流水线（另一个对话）按什么标准算"实现完成"。

## 4. 设计约束（owner 硬要求，逐条落实）

1. **忠于需求**：以第 2 节材料 1、2 为准，不自我发挥；要改需求就明确指出并说明理由。
2. **全自动闭环**：任何"人工粘贴/保存/点按钮"的环节都是设计缺陷，指出来并消灭。
3. **可复用**：能固定成 skill 的就固定成 skill，能记成知识的就记成知识。
4. **整体效果优先**：某个关键效果达不到、超期完成不了——设计上就要有"及时汇报、跳过、先做下一部分"的机制，不许卡死整体。
5. **知识优先用 OKF**：思考素材只从 OKF 取，缺口如实标注。
6. **人在环里是评判官**：评判动作要省人（卡片化、结构化），不是消灭人。
