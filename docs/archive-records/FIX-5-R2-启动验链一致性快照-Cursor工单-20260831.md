## 二、监理已逐字确认的根因

当前 `AiAssistantStore.AuditChain.cs`：

```text
VerifyAllAuditChainsOnConnection()
  -> LoadAllTaskStepsGrouped()   // SELECT 明细
  -> LoadAllAnchors()            // 另一条 SELECT 尾锚
  -> VerifyAllTasks(...)
```

两次读取没有共同 `SQLiteTransaction`。在 WAL 下，每条独立 SELECT 可看到不同提交时点：

1. 验链读到明细尾序号 N；
2. 另一进程原子追加 N+1 并同步更新尾锚后提交；
3. 验链再读到尾锚 N+1；
4. 完整账本被误报 `anchor_tail_sequence_mismatch`，`Initialize` 将 `AuditIntegrityFailed=true`，后续 `EnsureWriteReady` fail-closed 禁写。

证据：

- Cursor 全量：A1 同进程双 store 与 A2 双进程同时红；各自单跑可绿。
- 监理将 A1+A2 联合连续运行 5 轮，A2 在第2、第5轮失败，**2/5 可复现**；不是可豁免的偶发。
- 当前 HEAD 监理单次全量 909/909 可绿，只说明竞态未在该次命中，不能推翻 2/5 证据。

## 三、冻结修复合同

1. `VerifyAllAuditChainsOnConnection` 对“全部明细 + 全部尾锚”的读取必须来自**同一个 SQLite 读快照**。
2. 推荐使用 System.Data.SQLite 的 deferred/read transaction（需在代码/测试中实证具体 IsolationLevel 行为），并把同一 transaction 显式传给：
   - chain_version 列探测；
   - 明细 SELECT；
   - 尾锚 SELECT。
3. 不得使用现有 `BeginWriteTransaction()`/Serializable 的 `BEGIN IMMEDIATE` 把验链变成抢写锁；启动验链是只读操作，在 WAL 下不得无故阻塞合法并发写。
4. 读事务必须在成功/异常两条路径正确结束；不得留下连接事务或锁。
5. 真断链仍必须 fail-closed，现有 `missing_tail_anchor`、`orphan_anchor_empty_chain`、`anchor_tail_sequence/hash/version_mismatch` 等判断一律保留。
6. 禁止通过以下方式假修：
   - catch 后忽略 mismatch；
   - mismatch 时重新读到碰巧一致；
   - sleep/retry；
   - 把验证移到写后或关闭启动验链；
   - 给 A1/A2 加 skip、放宽断言或只禁测试并行。
7. 不改追加写事务、尾锚九字段、canonical hash、V1/V2 续链、迁移、recovery/takeover 顺序。

若 System.Data.SQLite 在本项目中无法提供“同快照且不抢写锁”的 read transaction，停工报告实测，不得自行改成 BEGIN IMMEDIATE；可提出单 SQL 快照读取备选，由监理再裁决。
