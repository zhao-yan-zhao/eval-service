## 2. 冻结合同（五条全文，唯一验收依据）

### 合同 1（D-06 原子追加，冻结版）

审计序号以 `task_id` 为作用域，从 1 开始严格连续。所有能够向 `ai_task_steps` 追加记录的路径，包括公开 `AppendTaskStep`、`AppendAuditRepairAtomic`、状态提交内的 `AppendTaskStepOnConnection` 及后续新增路径，必须统一进入同一个事务化追加原语。

该原语必须在同一个 SQLite 数据库级 write-reserved 串行写事务中完成：

1. 读取该任务当前尾锚及最后一条链记录；
2. 校验尾锚与链尾一致；
3. 分配 `next_sequence = tail_sequence + 1`，空链为 1；
4. 确定 `prev_hash`；
5. 按目标链版本计算 `entry_hash`；
6. 插入 `ai_task_steps`；
7. 更新该任务尾锚；
8. 提交事务。

应使用数据库级 `BEGIN IMMEDIATE` 或经所用 `System.Data.SQLite` 版本验证为等价 write-reserved 的事务 API。应用层进程内锁仅可用于减少竞争，不得作为跨连接或跨进程正确性边界。

必须保留并迁移后核验数据库约束 `UNIQUE(task_id, sequence_no)`；不得改成全库 `sequence_no` 唯一。

任一步骤失败必须回滚整笔事务。回滚后不得存在：

- 已插入链行但尾锚未更新；
- 尾锚已更新但链行不存在；
- 两条记录占用同一任务同一序号；
- 两条已提交记录引用同一前驱形成分叉；
- 仅提交任务状态、runtime 或其他业务数据而缺少其合同要求的审计行。

事务竞争采用有界 busy timeout/重试；超过上限返回明确的审计写失败，不得绕过事务降级为非原子追加。失败事务未提交的序号可由后续成功事务重新分配，这不构成"序号已占"。

### 合同 2（D-05 链 V2，冻结版）

`ai_task_steps` 新增非空整数字段 `chain_version`。迁移时既有记录统一赋值为 `1`；迁移完成后所有新追加记录必须写入 `2`。调用者不得自行指定或降级链版本，版本由存储层决定。

V1 验证算法必须逐字保持现有规则，不得重算或改写既有 V1 的 `prev_hash`、`entry_hash` 或业务字段。

V2 的 canonical 输入必须至少包括以下字段，并固定字段顺序、类型、空值和 UTC 格式：

1. `chain_version`
2. `step_id`
3. `task_id`
4. `sequence_no`
5. `kind`
6. `status`
7. `diagnostic_id`
8. `tool_name`
9. `request_summary`
10. `response_summary`
11. `retry_no`
12. `started_at_utc`
13. `ended_at_utc`
14. `prev_hash`

V2 canonical 必须采用无歧义编码，例如固定 UTF-8 的长度前缀编码；不得仅以裸分隔符拼接未转义字段。`entry_hash` 继续使用 SHA-256、小写十六进制输出。

同一任务允许且只允许以下版本形态：全部 V1；或连续 V1 前缀后接连续 V2 后缀。不允许从 V2 回退至 V1，也不允许交错版本。

第一条 V2 记录的 `prev_hash` 必须引用该任务最后一条 V1 记录的 `entry_hash`；若任务为空，则 `prev_hash` 为空。版本切换不得创建第二条独立链。

`VerifyChain` 必须：按 `sequence_no` 严格验证从 1 连续；按每行 `chain_version` 选择 V1 或 V2 算法；验证相邻行 `prev_hash`；验证版本只能单调从 V1 升到 V2；对未知版本、空版本、版本回退、序号重复或缺口一律失败。

V1 的已知限制必须保留在兼容声明中：V1 的 `StepId` 不受其链哈希保护；只有 V2 及以后保证修改 `StepId` 可被验出。

### 合同 3（事务化尾锚与启动验链，冻结版）

为每个存在审计链的 `task_id` 保存一条独立尾锚，至少包含：`task_id`、`tail_sequence`、`tail_hash`、`tail_chain_version`、`anchor_version`、`updated_at_utc`、预留的认证字段（见合同 5）。

每次审计追加必须在插入链行的同一个 SQLite 事务中插入或更新对应尾锚。事务提交后必须满足：空链不存在尾锚；非空链恰有一条尾锚；`tail_sequence` 等于该任务最大 `sequence_no`；`tail_hash` 等于该尾行 `entry_hash`；`tail_chain_version` 等于该尾行 `chain_version`。

初始化与生产启动顺序必须为：

1. 完成 schema 迁移；
2. 对全部任务执行完整 `VerifyChain`；
3. 比对每个任务的尾锚，并检查孤立锚、缺失锚和多余链；
4. 仅在全部通过后，允许执行 orphan recovery、`RecoverOnStartup`、startup takeover、任务恢复或任何新的 AI 写操作。

验链或尾锚比对失败时：

- AI runtime 进入持久到本次进程结束或显式重新验证成功为止的 `audit_integrity_failed` 状态；
- 禁止创建/继续/暂停/恢复/取消/完成 AI 任务；
- 禁止模型请求、工具调用、AI 场景写入、恢复确认、清除 recovery/inflight sentinel；
- 禁止任何 `ai_task_steps` 追加以及会与审计步骤组成原子业务提交的任务状态/runtime 写入；
- 不得在损坏链上追加"验链失败"记录；
- 允许只读查看、诊断和导出审计数据及完整性错误；
- F1 非 AI 宿主可以继续运行，但仍必须遵守既有 recovery/inflight 场景保护，不能因 AI runtime 禁用而自动清除锁或 sentinel。

验链失败不得由 `RecoverOnStartup` 当前的 best-effort catch 吞掉并继续启用 AI。生产 runtime 可按现有初始化失败模式返回 disabled runtime，但不得使整个 F1 宿主退出。

### 合同 4（旧库迁移，冻结版）

旧库采用"双版本共存、V1 原样保留、后续写 V2"的迁移方案，不执行 V1→V2 历史重哈希。

**阶段 A：证据保护与预检**

1. 在修改 schema 前，通过 SQLite 一致性备份机制生成包含已提交 WAL 内容的旧库证据副本；不得用可能遗漏 WAL 的普通热文件复制替代。
2. 按现有 V1 算法验证所有既有 `ai_task_steps`。
3. 若任一任务存在序号缺口/重复、`prev_hash` 不匹配、`entry_hash` 不匹配或不可读取记录，则判定旧库已断链。

**阶段 B：完整旧库迁移**（所有 V1 链完整时，在一个迁移事务中）

1. 新增 `chain_version INTEGER NOT NULL DEFAULT 1`；
2. 创建独立尾锚表及约束；
3. 从每个任务的实际 V1 尾行生成尾锚；
4. 核验 `(task_id, sequence_no)` 唯一约束仍存在；
5. 写入 schema migration 版本；
6. 提交。

迁移后不修改任何既有 V1 行的业务字段、`prev_hash` 或 `entry_hash`；后续新增行统一按 V2 追加，并连接到原 V1 尾部。

**已断链旧库处置**：保留原数据库和一致性证据副本；不重算历史哈希；不删除损坏行；不插入伪造缺失行；不从最后"看似有效"的行另起 V2 链；不生成会把当前损坏尾部追认为可信状态的尾锚；返回 `audit_integrity_failed`，按合同 3 禁止 AI 写入及场景操作；仅允许只读诊断和导出。

本批不提供自动修复性续链。未来如需人工处置，必须设计为单独的、显式授权的证据封存/新账本协议，不能伪装成正常迁移。

### 合同 5（预留升乙，冻结版）

本批仅实现威胁模型甲，不实现签名、HMAC、密钥生成、密钥存储、密钥轮换或外部锚定。

数据结构必须为未来 V3 预留以下扩展点：链行具有显式 `chain_version`；尾锚具有独立 `anchor_version`；尾锚预留可空字段 `auth_scheme`、`key_id`、`auth_tag`。

V2 写入时：`chain_version = 2`、`anchor_version = 1`、`auth_scheme`/`key_id`/`auth_tag` 均为空。

未来 V3 可以定义新的 canonical/HMAC 规则并写入新的认证字段，但必须：按版本验证既有 V1/V2 数据；不重写 V1/V2 的 `entry_hash`；不把 V3 认证字段反向解释成 V2 的组成部分；允许 V3 从既有 V2 尾部继续追加；未知 `chain_version` 或 `anchor_version` 必须 fail-closed。

当前预留字段不提供抗有权限者离线改库能力；在威胁模型甲下，攻击者同时修改链与库内尾锚并重算仍不在防护范围内。

## 6. L1 验收反例清单（最低集，完事报告须逐条映射测试名）

**A. 并发追加**
- A1 同任务、同进程、两个独立 store 并发各写 N 条：最终恰 2N 条，sequence 1..2N 无重复无缺口，prev_hash 正确，VerifyChain 过，尾锚=最后一行。
- A2 两进程/独立连接并发写同一任务：同 A1 断言（仅 Parallel.Invoke+单连接不算数）。
- A3 不同任务并发：各自从 1 连续、各自尾锚正确、不串链。
- A4 锁竞争：一连接持 write-reserved 事务，另一连接追加——有界 timeout/retry 后明确失败或等待后成功；不得出现未加锚的行；不得绕过事务追加。

**B. 事务中途失败回滚**（故障注入点：①读尾后 INSERT 前 ②INSERT 后锚更新前 ③锚更新后 COMMIT 前 ④外层业务已写、审计 INSERT 前 ⑤审计 INSERT 后、外层 COMMIT 前）：每个故障后重开 DB，断言链行数不变、尾锚不变、业务数据无部分提交、后续追加拿到正确下一序号、全链可验。另做进程强杀/掉电近似测试（不只测显式 Rollback）。

**C. 篡改检测**
- C1 改 V2 中间行/尾行 `step_id` → VerifyChain 败、启动进 `audit_integrity_failed`；V1 同类修改作为已知兼容限制单独测试，不得错误期待 V1 检出。
- C2 删尾行 → 逐行哈希可能仍过，但尾锚比对必须败；删中间行 → sequence gap/prev mismatch 检出。
- C3 改 `request_summary`/`response_summary`/`tool_name`/`status`/时间字段（中间行+尾行各至少一次）→ 哈希验出。
- C4 改 `chain_version`（V2→1、未知值、V2→V1 回退）→ fail-closed。
- C5 只改尾锚 sequence/hash/version → 锚比对检出。

**D. 旧 V1 库迁移**
- D1 完整纯 V1 库：迁移前字节级记录所有 V1 行；迁移后旧行 `chain_version=1`、原哈希与业务字段不变；尾锚指向 V1 尾；首条新记录为 V2 且引用 V1 尾 hash；混合链验过；二次启动迁移幂等。
- D2 空任务：不生成伪造 sequence 0 行、不生成非空尾锚；首次追加=V2 sequence 1。
