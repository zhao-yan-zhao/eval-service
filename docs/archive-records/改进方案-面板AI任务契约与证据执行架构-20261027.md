# 面板 AI 任务契约与证据执行架构改进方案

- 日期：2026-10-27
- 状态：设计建议稿，尚未实施
- 适用系统：`demo-ui/proxy`、③段想定生成与推演、④段统计评估
- 触发案例：操作员要求“复制想定里同型号的船，修改推进速度并实测”，面板 AI 自行转向改库选型，并作出证据不足的推进数据判断

---

## 一、结论与改造目标

### 1.1 核心结论

本次事故不是某个船型、某条提示词或某个正则表达式的孤立错误，而是共同架构缺口：

> 系统已经具备规矩注入、工具白名单、写库授权、可信回执、局部任务状态和回复核查，但缺少一份贯穿“用户目标—执行步骤—对象身份—证据要求—完成条件”的统一任务契约。

结果是：

1. 模型可以把“复制想定单位”自行替换为“选择数据库平台改型”，系统无法识别目标漂移。
2. skill 写明了流程，但是否执行、执行到哪一步仍依赖模型自觉。
3. 工具调用很多，不等于问题查清；查询样本与结论范围没有绑定。
4. 回复核查主要识别完成态、数值、哈希和绑定，无法覆盖“没有记录”“全库唯一”“速度来源于想定”等存在性、全称性和因果性判断。
5. 业务步骤散落在提示词、skill、`server.mjs` 特判和 `claimcheck.mjs` 文本猜测中，后续每起事故都会继续制造补丁。

### 1.2 改造目标

建立统一的“任务契约 + 持久状态 + 证据验收”机制，使系统能够：

- 锁定用户目标，未经明确变更不得更换对象、作用层或验证目标；
- 把自然语言请求转成可执行、可恢复、可审计的步骤集合；
- 由执行层真实回执推进步骤，模型不能自行宣布完成；
- 对不同类型的结论要求不同类型证据；
- 未查询、样本不足、字段缺失、记录不存在、引擎机制未验证分别表达，不得混用；
- 修改与实测分离，未实测不得报“改完生效”；
- 保留现有写库授权、租约、阶段门和可靠队列，不另开绕门通道。

### 1.3 非目标

本方案不追求：

- 用一套正则理解所有自然语言；
- 用大模型自行生成任意代码并在生产环境执行；
- 用更多提示词替代工具能力建设；
- 一次性重写全部四阶段；
- 删除所有安全校验或让模型绕过人工授权；
- 为本次自爆艇单独编写硬编码分支。

## 二、现状与根因

### 2.1 现有能力

| 模块 | 已有能力 | 当前缺口 |
|---|---|---|
| `skills.mjs` | 按阶段注入 skill 全文 | 只有文本规范，没有机器可执行的任务步骤 |
| `prompts.js` | 阶段职责与部分铁律 | 把“是否有工具调用”误作任务是否合法的粗粒度判据 |
| `tools.mjs` | 工具 schema、参数校验、白名单 | 工具定义与业务流程、重复确认门说明混杂 |
| `dbgate.mjs` | 写库方案、确认、范围、TTL、撤销、授权承接 | 只管授权，不管完整业务目标与后续实测 |
| `task-state.mjs` | 持久步骤、回执核验、授权、等待、恢复 | 只覆盖授权、推演续办、统计续办等局部步骤 |
| `operation-receipt.mjs` | 可信执行回执、事实与目标字段 | 多数 `db3k.*` 回执缺少可用于语义验收的结构化 facts |
| `claimcheck.mjs` | 完成态与部分数值事实核查 | 依赖文本正则，无法可靠判断任务是否完成 |
| `reliable-queue.mjs` | 至少一次续办、对账、幂等和阻断 | 需要更明确的步骤身份与副作用幂等键 |

### 2.2 本次暴露的直接问题

1. 现有工具已提供 `unit.add` 和 `unit.update(speed)`，因此“复制想定单位并改单位速度”和“复制数据库平台并改推进记录”是两条不同链路，不能默认互相替换。
2. 当前初始任务没有完整步骤声明；`db.present_plan` 成功后才临时追加授权步骤。
3. `matchStepForTool()` 根据工具名猜测步骤归属，无法防止“工具相同但目标不同”。
4. 工具成功只代表调用成功，不代表所得信息足以支持最终结论。
5. 留档摘要不等于完整证据；应保留可复核的结构化结果或其受信引用。

### 2.3 共同根因

系统目前缺少以下五个统一概念：

- `Goal`：用户真正要得到的结果；
- `Target`：操作对象及其不可漂移的身份；
- `Plan`：完成目标所需的步骤和依赖；
- `Evidence`：每一步可验收的结构化事实；
- `Claim`：最终允许输出的结论及其证据范围。

## 三、总体设计

### 3.1 架构原则

1. **模型负责理解与提议，服务端负责校验与推进。**
2. **任务定义与任务运行分离。**契约模板定义“应该做什么”，状态机记录“实际做了什么”。
3. **对象先于工具。**先锁定操作对象，再决定工具；不得因为某工具更容易就换对象。
4. **证据先于结论。**任何事实结论必须绑定证据和适用范围。
5. **修改不等于生效，生效必须有对照验证。**
6. **失败可分类、可恢复。**能力不足、授权等待、查询为空、结果不确定不得混成一种失败。
7. **安全门原样保留。**任务契约只能调用既有授权接口，不得绕过。
8. **渐进替换。**先影子运行，再按模板逐项强制，不做大爆炸重写。

### 3.2 模块划分

新增：

- `demo-ui/proxy/task-contract.mjs`
  - 任务契约 schema；
  - 模板注册表；
  - 草稿校验；
  - 步骤依赖与证据谓词；
  - 目标漂移检查；
  - 结论证据规则。

扩展：

- `demo-ui/proxy/task-state.mjs`
  - 作为唯一持久运行状态机；
  - 保存契约版本、目标快照、步骤依赖、当前步骤和证据；
  - 提供下一可执行步骤；
  - 不接受模型直接设置完成状态。

调整：

- `server.mjs`：只负责协议接入、调用执行器、写入事实和返回状态；
- `operation-receipt.mjs`：补齐结构化 facts、对象身份和完整结果引用；
- `claimcheck.mjs`：逐步转成通用“输出结论是否有证据”的兜底核查；
- `prompts.js`：恢复为薄职责提示；
- `tools.mjs`：只描述工具能力、参数和安全边界。

明确不改：

- `dbgate.mjs` 继续作为写库授权唯一裁决者；
- `guard.mjs` 继续负责租约、冻结和作业安全；
- `reliable-queue.mjs` 继续负责可靠投递，不承担业务规划。

## 四、任务契约设计

### 4.1 任务契约结构

建议使用 `task-contract/v1`：

```json
{
  "schema_version": "task-contract/v1",
  "contract_id": "server-generated-id",
  "template_id": "scenario.unit.speed.verify",
  "template_version": 1,
  "goal": {
    "kind": "modify_and_verify",
    "requested_outcome": "复制指定想定单位，调整速度并验证实际效果",
    "success_metric": "copied_unit_measured_speed_matches_target"
  },
  "target": {
    "layer": "scenario_unit",
    "scenario_path": null,
    "side": null,
    "unit_id": null,
    "unit_name": null,
    "dbid": null,
    "db_path": null
  },
  "constraints": {
    "target_mutable": false,
    "allow_layer_change": false,
    "allow_database_write": false,
    "preserve_source": true,
    "max_write_attempts": 1
  },
  "parameters": {
    "requested_speed_kts": null,
    "verification_duration_seconds": null
  },
  "steps": [],
  "completion": {
    "required_steps": [],
    "required_claims": []
  }
}
```

### 4.2 目标锁定规则

1. `target.layer` 至少区分：
   - `scenario_unit`：想定中的一个具体单位；
   - `database_platform`：数据库中的平台/组件；
   - `scenario_rule`：想定规则、任务或条令；
   - `experiment_variable`：实验变量；
   - `analysis_only`：只读分析。
2. 用户原话明确“想定里的船”时，默认目标为 `scenario_unit`。
3. 模型认为应改走数据库链路时，必须返回 `target_change_required`，说明原因，由用户明确选择；不得自行换成驱逐舰或其他平台。
4. 目标变化后：
   - 原契约标记 `superseded`；
   - 生成新契约和新计划；
   - 原写库授权不得自动继承；
   - 已产生的只读证据只能作为背景，不能冒充新目标证据。
5. 若缺少速度值等必要参数，只询问阻塞执行的参数；能通过只读查询获得的不得问用户。

### 4.3 步骤结构

```json
{
  "stepId": "identify-source-unit",
  "label": "核定源单位",
  "kind": "read",
  "depends_on": ["load-scenario"],
  "allowed_tools": ["unit.status"],
  "input_bindings": {
    "side": "$.target.side",
    "unit_id": "$.target.unit_id"
  },
  "evidence_requirements": [
    {
      "fact": "unit_identity",
      "required_fields": ["unit_id", "name", "side", "dbid"],
      "match_target": ["unit_id", "side"]
    }
  ],
  "on_missing": "blocked_target_not_found",
  "on_ambiguous": "request_target_disambiguation",
  "completion": "all_evidence_requirements_met"
}
```

要求：

- 步骤只能由契约模板或服务端校验后的计划创建；
- 模型不得直接传入 `status=completed`；
- 工具成功但 facts 不完整时，步骤保持 `pending/blocked`，不得完成；
- 每次工具执行显式绑定 `contract_id + stepId + attemptId`；
- 写操作必须绑定目标对象、授权代次和幂等键；
- 每一步记录 `not_checked / checked_empty / checked_present / uncertain`，禁止把未检查当空值。

### 4.4 证据谓词

采用声明式谓词，不执行模型生成的表达式：

- `all` / `any` / `not`；
- `exists` / `equals` / `not_equals` / `in`；
- `is_null` / `is_missing` / `is_empty`；
- `count_equals` / `count_at_least`；
- `same_target` / `same_run` / `same_contract`；
- `before_after_changed` / `before_after_unchanged`；
- `enumeration_complete`；
- `controlled_comparison`。

禁止 `eval`、任意 JavaScript、任意 SQL 作为验收谓词。

## 五、两条改速链路必须分开

### 5.1 想定单位链路：`scenario.unit.speed.verify`

适用：用户要复制想定中的单位并调整该单位速度。

推荐步骤：

1. `scenario.list`：核定授权目录与实际想定路径；
2. `scenario.load`：装载目标想定；
3. `unit.status`：锁定源单位 `unit_id/side/name/dbid` 和必要状态；
4. 若缺速度目标值，向用户只询问该参数；
5. `unit.add`：按相同 DBID 和必要配置创建副本；
6. `unit.status`：读回新单位身份，证明复制对象正确；
7. `unit.update(speed)`：只修改新单位，不修改源单位；
8. `unit.status`：读回设置值；
9. `scenario.save`：另存最小对照候选，不覆盖源想定；
10. `simulation.run`：有界起跑；
11. `simulation.status`：等待真实终态；
12. `measurement.read`：读取同局、同新单位实测速度；
13. 对照目标值、设置值和实测值，输出结论。

完成条件：

- 新单位身份与源单位 DBID 一致；
- 源单位未被修改；
- 设置值读回成功；
- 实测证据属于同一 `run_id` 和新 `unit_id`；
- 若实测不一致，只能报告“设置成功但未达到目标实测效果”，不得报任务成功。

### 5.2 数据库平台链路：`database.platform.propulsion.verify`

适用：用户明确要修改平台推进记录，或单位链路经证据确认无法满足需求且用户同意切换。

推荐步骤：

1. 核定想定、单位和 DBID；
2. `db3k.dbinfo`：锁定当前数据库；
3. `db3k.detail` / `db3k.relations`：读取平台与推进关系；
4. `db.lookup`：查询引用影响面；
5. 区分 `record_missing`、`speed_field_null`、`speed_field_present`；
6. `db.present_plan`：呈报对象、原理、风险、影响和验证方式；
7. 用户明确确认，`db.confirm_gate` 登记授权；
8. `db.copy_for_edit`：创建工作副本；
9. 按既有规则递归复制平台/组件并保留快照；
10. `db.run_sql_script`：一次一处修改并读回；
11. 完整性、行数、哈希和关联关系校验；
12. 绑定副本库，另存最小对照想定；
13. 有界推演并读取实测速度；
14. 报告数据库读回值与实测效果，二者不得互相替代。

授权边界：

- 任务契约只声明 `requires_authorization=true`；
- 是否授权仍由 `dbgate.mjs` 决定；
- 契约不得自行确认、扩大数据库路径或复用其他任务授权。

### 5.3 能力缺口处理

若当前工具不能完成用户指定层级的操作：

- 返回 `capability_blocked`；
- 明确缺少哪个动作或字段；
- 不得自动改走另一条链路；
- 可以提供替代方案，但必须由用户选择后建立新契约。

## 六、证据与结论规则

### 6.1 证据类型

| 结论类型 | 必需证据 | 禁止推导 |
|---|---|---|
| 记录不存在 | 明确查询范围 + 空结果 + 查询成功 | 不得由详情截断、字段缺失或搜索词无匹配推出 |
| 字段为空 | 记录存在 + 字段存在 + 值为 null/空 | 不得写成“没有推进记录” |
| 字段未返回 | 回执缺字段或结果被截断 | 不得写成字段为空 |
| 全库唯一 | 全量枚举范围、总数、筛选条件、完整检查结果 | 不得由几十个样本推出 |
| 样本中唯一 | 样本清单和样本范围 | 不得省略“在已查样本中” |
| 数据来自某处 | 直接字段证据或受控对照实验 | 不得由另一处为空推出 |
| 修改已写入 | 写回执 + 读回值 + 对象身份 | 不得由脚本执行成功单独推出 |
| 修改已生效 | 同对象同局实测 + 对照 | 不得由数据库读回或界面设置值推出 |
| 引擎存在限制 | 最小对照排除实现和设计因素 | 不得由单次异常直接归因引擎 |

### 6.2 结论结构

最终报告中的事实结论使用统一结构：

```json
{
  "subject": {"kind": "ship", "id": 4468},
  "predicate": "propulsion_speed_field",
  "value": null,
  "qualifier": "current_database",
  "scope": {
    "db_path": "受信路径",
    "enumeration_complete": false
  },
  "evidence_operation_ids": ["executor-receipt-id"],
  "confidence": "verified"
}
```

`confidence` 只允许由服务端根据证据生成：

- `verified`：证据完整且一致；
- `contradicted`：证据与结论冲突；
- `unverified`：缺证据；
- `out_of_scope`：结论范围大于证据范围。

模型可以提议结论，但不能自行把 `unverified` 改成 `verified`。

### 6.3 完整结果留档

当前前端摘要可以继续截断，但执行层必须保留：

- `operation_id`；
- 完整结构化结果或受信结果文件引用；
- 结果哈希；
- 工具、参数、对象、时间；
- 是否完整、是否截断、截断位置；
- 模型收到的投影字段清单。

建议为 `db3k.detail` 增加字段投影，例如 `fields:["identity","propulsion"]`，避免模型反复调用同一详情接口寻找被省略字段。投影只减少模型上下文，不得删除原始留档。

## 七、执行控制与模型角色

### 7.1 开工流程

1. 服务端收到用户消息；
2. 模型生成 `TaskDraft`，只能选择已注册模板并填写结构化参数；
3. 服务端校验：
   - 模板存在且阶段允许；
   - 用户目标与模板语义一致；
   - 目标未漂移；
   - 参数完整；
   - 工具均在白名单；
   - 写操作有授权节点；
   - 验证步骤不可省略；
4. 服务端生成 `contract_id`，持久化契约和步骤；
5. 每轮向模型提供当前步骤、允许工具、已知事实和缺失证据，而非重新让模型规划全流程；
6. 工具结果生成可信回执，状态机按证据谓词推进；
7. 所有必需步骤完成后才允许最终报告。

### 7.2 模型每轮看到的内容

```text
当前目标：复制指定想定单位并验证速度
不可变更：目标单位、作用层、源想定
当前步骤：读回复制单位
允许工具：unit.status
已完成证据：scenario.load / unit.add 对应回执
缺失证据：新单位 unit_id 与 dbid 读回
禁止：改选其他船型、转入改库、宣布实测完成
```

### 7.3 非执行任务

纯问答、解释和只读分析使用 `analysis_only` 契约：

- 允许零工具，但只能基于已有材料并明确引用；
- 一旦输出当前状态、数值或全库结论，就必须有相应证据；
- 不得套用“纯叙述轮一律无效”的旧规则；
- 解释性回答不能推进执行任务步骤。

### 7.4 重复调用控制

状态机记录：

- 同一 `stepId + tool + normalized_args` 的调用次数；
- 返回结果哈希是否变化；
- 缺失证据是否变化。

相同调用连续两次返回相同结果且没有新增证据时：

- 停止重复调用；
- 返回 `no_new_evidence`；
- 引导使用字段投影、补充查询或报告缺口；
- 不得通过更换无关平台制造“正在推进”的假象。

## 八、回复核查改造

### 8.1 新主路径

最终回复由两部分组成：

1. 模型生成自然语言；
2. 模型同时提交结构化 `claims[]`，每项引用 `evidence_operation_ids`。

服务端检查：

- 回执存在且属于当前任务；
- 回执来源为执行层；
- 对象、数据库、想定、runId 与结论一致；
- 证据谓词满足；
- 结论范围不超过证据范围；
- 所有必需步骤完成前不得输出完成类结论。

### 8.2 旧核查器保留边界

迁移期保留 `claimcheck.mjs` 作为最后兜底；结构化契约上线后：

- 删除重复的业务动词到工具映射；
- 删除已由结构化 claims 覆盖的速度、哈希、绑定专用文本抽取；
- 保留通用伪造系统告示、无证据完成态和证据身份校验；
- 不再通过不断新增中文正则追赶每一种事实表达。

## 九、界面与交互

### 9.1 任务状态展示

面板至少展示：

- 当前目标；
- 当前对象和作用层；
- 当前步骤；
- 等待原因；
- 已完成证据；
- 尚缺证据；
- 是否等待授权；
- 是否已完成实测。

### 9.2 选择卡使用边界

选择卡只用于真正的用户决策：

- 改变目标或作用层；
- 批准改库方案；
- 补充无法只读获得的必要参数；
- 在能力缺口下选择替代方案。

不得用选择卡替代系统本应完成的只读核查，也不得把“换一艘更容易的船”作为默认推荐来覆盖原目标。

### 9.3 失败表达

统一区分：

- 等待用户参数；
- 等待写库授权；
- 目标不存在或有歧义；
- 工具能力缺口；
- 证据不足；
- 修改成功但实测未达目标；
- 执行结果不确定，需要系统侧对账。

## 十、现有代码改造与删除清单

### 10.1 `server.mjs`

改造：

- 开工时创建并校验契约；
- 工具调用携带受信 `contract_id/stepId/attemptId`；
- 回执直接归入明确步骤；
- 删除业务流程特判后，仅保留协议适配。

迁移后删除：

- `recordToolReceipt()` 中 `db.present_plan` 临时声明 `auth-db-*` 的特判；
- `matchStepForTool()` 的工具名猜步骤逻辑；
- `declareRunContinuationSteps()` 和 `declareStatsContinuationSteps()` 中已迁入通用模板的重复步骤拼装。

### 10.2 `task-state.mjs`

保留并扩展：

- 持久化；
- 回执严格核验；
- 授权、等待、失败和恢复；
- 可靠队列对账。

新增：

- 契约版本与目标快照；
- 步骤依赖；
- evidence requirements；
- 重复调用无新证据检测；
- 目标变更使旧契约失效；
- 完成前全量验收。

不得新增：

- 模型直接完成步骤的 API；
- 仅凭工具 `ok=true` 完成语义步骤的捷径。

### 10.3 `prompts.js`

删除：

- “每轮必须执行全部工具”；
- “纯叙述轮零工具一律无效”；
- 与任务契约重复的流程裁决。

保留：

- 阶段职责；
- 表达规范；
- 使用选择卡和产物登记的基本交互要求。

### 10.4 `tools.mjs`

收敛：

- 工具只声明能力、参数、效果和副作用；
- 改库授权说明统一由 `dbgate.mjs` 生成；
- 删除多处重复确认门长文案。

新增或完善：

- `db3k.detail` 字段投影；
- `unit.status` 必要身份和速度字段的稳定返回；
- 写操作 before/after/diff 与读回证据。

### 10.5 `claimcheck.mjs`

在结构化 claims 覆盖后删除：

- 已被通用证据校验替代的领域专用正则；
- 重复的工具/动词证据映射；
- 只针对单一事故措辞的补丁。

保留：

- 通用输出证据核查；
- 伪造系统告示检测；
- 未验证结论降级与审计。

### 10.6 skill 文件

不删除领域知识，但调整职责：

- 保留安全规则、领域经验、工具能力边界和诊断方法；
- 通用执行顺序以契约模板为唯一机器事实源；
- skill 与模板冲突时，应停止并报配置不一致，而不是由模型自由选择；
- 建立模板与 skill 条目的静态一致性检查，防止双份规则长期漂移。

## 十一、迁移实施顺序

### 阶段 0：回归基线与影子契约

- 固化本次会话及同类失败案例；
- 建立 `TASK_CONTRACT_MODE=off|shadow|enforce`；
- `shadow` 只生成契约和预期步骤，不拦截旧流程；
- 对比模型实际调用与契约差异，补齐模板。

退出标准：核心案例均可生成合法契约，无误换目标、无绕授权计划。

### 阶段 1：证据底座

- 扩展回执 facts、目标身份和完整结果引用；
- 增加 `db3k.detail` 字段投影；
- 明确 `missing/null/empty/not_returned`；
- 建立结构化结果留档。

退出标准：4468、3151 等详情可凭回执独立复核，不依赖模型转述。

### 阶段 2：想定单位改速模板

- 上线 `scenario.unit.speed.verify`；
- 接管目标锁定、步骤推进和实测验收；
- 先只覆盖单单位复制、改速、短局测量。

退出标准：未经用户同意不会进入改库；未实测不会报完成。

### 阶段 3：数据库平台改型模板

- 上线 `database.platform.propulsion.verify`；
- 复用 `dbgate`、复制、SQL、快照、哈希、绑库和实测链路；
- 目标变更生成新契约和新授权范围。

退出标准：缺 `db.lookup` 不能呈报完成；未确认不能写；未实测不能报生效。

### 阶段 4：迁移既有续办

- 将推演续办、统计续办改为通用契约模板；
- 删除 server 中对应专用步骤拼装和猜测匹配；
- 保持可靠队列与恢复语义不变。

退出标准：既有续办测试全绿，重启恢复、迟到结果、重复通知和授权撤销不回归。

### 阶段 5：结构化结论与删旧

- 上线 claims 证据绑定；
- 将 claimcheck 收敛为通用兜底；
- 删除已覆盖的专用正则和重复提示词；
- 开启模板与 skill 一致性检查。

退出标准：新机制下旧事故用例全部被阻断或明确降级，旧代码无调用方。

## 十二、测试矩阵

### 12.1 目标与计划

1. “复制想定同型号船”必须生成 `scenario_unit`，不得默认改库。
2. 模型推荐改驱逐舰时，系统返回目标漂移，不执行。
3. 用户明确同意改库后，必须生成新契约，不继承旧目标。
4. 缺速度值时只询问速度，不重复询问可查路径和 DBID。
5. 多艘同名船时必须要求消歧，不得任选。
6. 目标不存在时停止，不得换成相似型号。

### 12.2 证据语义

7. 推进记录存在、速度字段为 null，只能输出“字段为空”。
8. 推进记录不存在，只能输出“该查询范围内无记录”。
9. 回执未返回字段，只能输出“未获得该字段”。
10. 搜索关键词无结果，不得推出平台不存在。
11. 抽查 40 个 ID，不得输出“全库唯一”。
12. 全量枚举完成后才允许输出全库唯一，并保留枚举范围。
13. 当前源库无 20001，不得推出副本库也无 20001。
14. 交接文档数值只能标为文档来源，不得冒充本轮实测。
15. 旧想定路径与新装载路径不一致时，禁止混用单位数量和状态。

### 12.3 执行与验收

16. `unit.add` 成功但未读回 DBID，复制步骤不得完成。
17. `unit.update` 成功但实测速度未达目标，只能报告未达目标。
18. 数据库读回速度正确但实测未变，不得报生效。
19. 实测必须匹配同一 `run_id + unit_id`。
20. 源单位被意外修改时，保持源不变验收失败。
21. 无 `db.lookup` 不得完成改库方案步骤。
22. 未确认不得复制或写库；撤销后旧授权不得复活。
23. 改 A 库的授权不得用于 B 库或名称相近库。
24. 同一工具同一参数重复返回相同结果两次，触发 `no_new_evidence`。
25. 工具结果截断且缺必需字段时，不得完成步骤。

### 12.4 恢复与安全

26. 浏览器关闭、代理重启后契约和当前步骤可恢复。
27. 重投不得重复复制单位、重复写库或重复起跑。
28. 执行结果不确定时先对账，禁止盲目重放。
29. 旧任务 v1 状态可读取；不能自动升级的任务保持只读或明确终止。
30. 契约与 skill 冲突时启动/加载检查失败，禁止模型自行择优。

## 十三、本次事故的验收剧本

输入：

> 你先复制个想定里同型号的船出来，然后把这个船的推进系统的速度改了，然后测一下。

系统必须满足：

1. 建立以“想定中的同型号单位”为目标的契约；
2. 装载并读取实际想定，锁定具体源单位；
3. 若“推进系统速度”存在单位速度与数据库推进档位歧义，只就这一作用层差异进行一次性澄清；不得擅自换成驱逐舰；
4. 选择单位链路时，使用同 DBID 新单位，修改新单位速度并读回；
5. 选择数据库链路时，先完成影响面和确认门，再复制修改；
6. 建立最小对照场景并实测；
7. 最终分别报告：复制是否成功、设置值、读回值、实测值、是否达到目标；
8. 任一环节未完成，最终状态保持未完成，并指出具体缺证步骤；
9. 全程禁止输出“当前库唯一”“引擎只能靠想定速”等超出证据范围的结论。

验收通过的关键不是最后一定改速成功，而是：

> 不换目标、不漏步骤、不伪造证据；能做到就做完，做不到就准确停在具体障碍处。

## 十四、观测指标与审计

新增指标：

- `target_drift_blocked_total`：目标漂移拦截数；
- `contract_step_completed_total`：按模板和步骤统计完成数；
- `contract_step_evidence_missing_total`：缺证阻断数；
- `unsupported_scope_claim_blocked_total`：结论范围扩大拦截数；
- `no_new_evidence_total`：重复查询无新增证据次数；
- `modify_without_measurement_total`：修改后未实测即试图完成次数，目标必须为 0；
- `unauthorized_write_attempt_total`：未授权写入尝试数；
- `task_recovery_success_total`：重启后成功恢复数。

每轮留档增加：

- `contract_id/template_id/template_version`；
- 用户目标与目标快照；
- 当前步骤及依赖；
- 每步证据谓词结果；
- 目标变更记录；
- 最终 claims 及证据引用；
- 未完成原因。

审计文件只追加，不覆盖旧记录；敏感路径和参数按现有脱敏规则处理。

## 十五、上线、灰度与回滚

### 15.1 灰度方式

- `off`：完全旧行为；
- `shadow`：生成契约和差异报告，不拦截；
- `enforce:scenario.unit.speed.verify`：只强制单位改速模板；
- `enforce:database.platform.propulsion.verify`：再强制数据库改型模板；
- 最后迁移推演和统计续办。

### 15.2 回滚

单模板关闭 enforce 即可回退旧流程；保留：

- `dbgate` 写库授权；
- 阶段门与租约；
- 可信回执；
- 可靠队列；
- 通用 claimcheck 兜底。

回滚不得删除已生成契约和审计记录；恢复后应能继续对账。

### 15.3 禁止事项

- 不得一次性删除旧 claimcheck 和续办逻辑后再补新实现；
- 不得在生产环境启用未接回执核验的 fixture 模式；
- 不得允许模型自定义验收谓词代码；
- 不得用“模型通常能答对”替代回归测试。

## 十六、风险与控制

| 风险 | 控制 |
|---|---|
| 模型生成错误模板 | 模板白名单 + 目标语义校验 + 目标漂移阻断 |
| 契约过于刚性，普通问答受影响 | `analysis_only` 与执行任务分离 |
| 证据适配工作量大 | 先覆盖两条改速链路，再逐模板扩展 |
| 状态机进一步复杂化 | 契约定义与运行状态分文件，server 不再堆业务特判 |
| 旧任务恢复失败 | schema 版本化、只读兼容、显式终止不可升级任务 |
| 结构化 claims 增加模型负担 | 服务端从步骤证据预生成 claims，模型只选择和表述 |
| 规则双写漂移 | 模板为机器事实源，skill 静态一致性检查 |
| 重复副作用 | 契约/步骤/尝试身份接入现有幂等与对账机制 |

## 十七、最终交付物与完成判据

实施完成应至少交付：

1. `task-contract.mjs` 及 schema、模板注册表；
2. `task-state.mjs` v2 状态与兼容迁移；
3. 两条改速模板及证据适配；
4. 完整结果留档与字段投影；
5. 结构化 claims 核查；
6. server、prompts、tools、claimcheck 的删旧清单与实际无调用证明；
7. 三十项核心回归测试及本次事故端到端复验；
8. shadow/enforce 灰度开关和回滚说明；
9. 审计字段与观测指标；
10. skill 与契约一致性检查。

最终完成判据：

- 同一输入连续运行时，目标与计划稳定，不随模型临时偏好换船、换库；
- 所有完成结论都能追溯到当前任务的真实证据；
- 样本结论、全库结论、字段为空、记录不存在和因果判断不再混用；
- 修改、读回、实测三种状态分别可见；
- 既有授权、安全、续办与恢复能力无回归；
- 新增同类任务只需注册契约模板和证据适配，不再修改多个提示词和正则文件。

## 十八、建议实施优先级

### P0：必须先做

- 目标锁定；
- 两条改速链路分离；
- 明确 stepId 的证据归属；
- 记录不存在/字段为空/字段未返回区分；
- 修改后实测才可完成；
- 本次事故回归测试。

### P1：随后完成

- 全库唯一的枚举证据；
- 重复查询无新证据控制；
- 结构化 claims；
- 推演与统计续办模板迁移；
- 重复提示词和专用 server 特判删除。

### P2：最后收敛

- 领域专用文本正则删旧；
- skill 与模板一致性检查；
- 更多改挂载、改条令、实验变量模板；
- 完整观测指标与长期事故回归库。

本方案的核心不是让 AI 在某艘船上答对一次，而是让它以后面对同类任务时，始终由系统保证：**目标不漂移、步骤可执行、证据可复核、结论不越界、未完成不冒充完成。**
