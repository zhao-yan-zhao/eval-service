## 三、审查项 A：飞机创建带 course 不生效

逐字定位：

- `unit.add` schema、参数归一化、tool registry和提示词。
- InMemory与生产 facade 的 `UnitAdd` 实现。
- 生产 Lua 生成/调用链中 `course` 如何传给 `ScenEdit_AddUnit` 或后续接口。
- 仓库内所有 `ScenEdit_AddUnit`、`ScenEdit_SetUnit`、航路点/course相关调用与测试。
- runs/中能对应“飞机请求带course但不移动、舰船正常”的真机证据；找不到写“未找到”。

必须回答：

1. 是参数形状、单位类型限制、调用时序，还是当前代码根本未执行飞机的二次设航线？只按磁盘证据定性。
2. 本机源码能否确认受支持的二次设航线 API 与参数形状？不能则设计最小真机探针。
3. 创建成功、设航线失败时应如何对用户呈现和进入恢复：
   - 方案A：`unit.add`内部自动二次设航线；任何第二步失败明确返回“单位已创建但航线未完成”，保留恢复/审计证据。
   - 方案B：创建与设航线保持两个工具步骤；`unit.add`对飞机带course明确拒绝或警告，要求模型随后调用位置/航线工具。
   - 如有更安全方案可另列，但不得默认“部分成功也算成功”。

给出推荐及优劣，重点从用户体验、部分成功风险、可回滚性说明。

- 固定设施与可移动设施在本机数据模型中能否可靠区分。

- 方案B：稳定版暂不承诺 Facility；schema/提示词和错误信息明确拒绝，避免当前“尝试后nil失败”。

分别说明用户可获得什么、实现风险、是否需要真机探针。若推荐A，必须先给出不污染正式场景的最小探针和失败后的清理/证据方案。

## 五、审查项 C：unit.status 分页

逐字定位：

- schema、默认/最大 `max_items`、生产查询实现、返回字段与当前截断行为。
- 当前结果是否有稳定排序；如果有，列出排序键；没有则标明分页前必须补稳定排序。
- 单 `unit_id` 查询与按 side 批量查询的分支。

比较并推荐：

- 方案A：`offset + limit`。实现和模型调用简单；查询期间单位增删时可能重复或漏项。
- 方案B：不透明 `cursor/next_cursor`。连续读取更稳，但合同和状态管理更复杂。

无论推荐哪种，必须冻结：最大页大小、稳定排序键、`has_more`、下一页字段、非法/过期游标错误码，以及单 `unit_id` 查询是否忽略分页参数。不得自行假设这些值，先给推荐值和理由供 owner 拍板。
