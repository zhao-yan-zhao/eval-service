## 技术侦察结论（Kimi 亲手读源码，方案的地基）

引擎库绑定机制（`Command_Core/DBOps.cs` ~530-560 行）：

1. 想定存的是**数据库哈希指纹**（加密载荷内），外层 XML 的 DBVersion 只是显示标签；
2. 引擎启动时扫描 DB 目录、算每个库的指纹、建"指纹→库"注册表；载入想定时**按指纹查注册表**，先注册先命中，查不到才报"想定数据库哈希值匹配失败"；
3. 整文件复制的改库副本与源库指纹相同 → 永远命中先注册的源库（昨晚三次回退的根因）；
4. F1 界面的手动切库是人工指定、绕开指纹解析，所以有效；
5. 桥载入路径 `Command/AiAssistantHost/HostScenarioReloader.cs:108` 走 `ClientCore.HandleScenarioLoaded`，与 UI 载入同路径——桥无罪，机制在解析层。

## 工作项

### W1 引擎库绑定根治（⑤c，最高优先，占编译窗口）

- **修法**：DBOps 解析函数改为——想定标签（DBVersion）写的库文件名在注册表中存在时**优先按文件名绑定**；文件名找不到再退回指纹解析；指纹命中库与标签库名不一致时**写显式警告日志**（从此不许静默）。改动面：一个函数 + 日志。
- **连带红利**：引擎按名字绑定后，"整文件复制"不再认错人——M6 遗留的"独立身份重建"（⑤a）大概率不需要了，W1 落地后重新评估，能省则省。
- **验收（Kimi 亲手）**：新库出生 → 重启 F1 → **桥载入**想定（无人工切库）→ 草稿探针=新库名；指纹不符时警告日志有记录；回归：绑定官方库的旧想定载入行为不变；80/108 各跑一局行为正确。
- **风险**：改的是所有想定载入的公共路径——必须做旧想定回归；改动文件改前备份+git 留痕。

### W2 轮次结构改造（①，纯 proxy/面板侧，与 W1 并行）

- **修法**：claim_check 判 marked 时 proxy **自动回炉重问**（"你的回复零工具调用被判无效，必须先调用工具再汇报"），最多 2 次；仍编造才带 ⚠ 标注下发（现行兜底）。这是"强制先调后报"的动态实现，立在已实弹验证的机制上，不改面板对话模型，成本最低。
