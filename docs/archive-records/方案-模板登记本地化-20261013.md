## 0. 结论速览

1. **`registration_sha256` 不含任何密钥/签名。** 它是 7 个明文字段的 `"\n"` 拼接再 SHA256，公式在桥源码里完全公开（`ApprovedTemplateRegistry.cs:110-130`）。本班对存量 4 条登记全部复算 **4/4 MATCH**（含 `manifest.sha256` 对账一致，见 §5 验证记录）。
2. **10-12 穷举失败的定性**：公式可本地复现——`register-m5-main.py` 2026-09-14 就写明公式且对存量 3 条实证 MATCH（脚本注释与 `verify_existing_formula()`）。穷举失败属拼接格式/字段取值未撞对，不是"审批信息不可复现"。且 10-12 报错停在 `template_registration_digest_mismatch`，说明前四关（manifest 摘要、条目唯一、请求 digest==登记 sha256）都过了——**他们的四件套写对了位置、manifest.sha256 也算对了，只差 registration canonical 最后一步**。
3. **审批链真实形态**：防滥用的硬闸只有三道——① registry 目录写权限（文件系统）；② 人工审批仪式（owner 定 `approved_by`/`approved_at` 留痕 + LAB-01/13 安检通过才 `--apply`）；③ 桥每次执行的 fail-closed 校验链（摘要对不上即拒、每次现算防 TOCTOU）。digest 链保证的是**完整性**（改过的文件必被抓），不保证**谁批的**——`approved_by` 是自述文本，任何能写目录的人都可写"owner-via-xxx"。
4. **Kimi 10-12 结论的准确表述**：审批链是设计、不是故障——对；但"审批信息不可本地复现"——错，公式+留痕字段全公开，已实证复现。本地化之后"谁能写 registry 目录"将成为唯一硬闸（公式随本方案公开），方案 A/C 均须默认接受这一点或由 owner 另行收紧目录 ACL。

## 1. 审批链全链路（源码证据）

### 1.1 登记物形态：四件套，纯文件
`ApprovedTemplateRegistry.cs:23-27` 定义 registry 目录内四个文件：
`manifest.json`（version=1 + templates 数组）、`manifest.sha256`（manifest.json 文件字节的 SHA256）、`<template_id>.lua`、`<template_id>.schema.json`。
体积上限：manifest ≤1MB、lua ≤1MB、schema ≤64KB（`:25-27`）。

### 1.2 registration_sha256 公式（逐字段）
`ApprovedTemplateRegistry.cs:110-130`，canonical = 按 `"\n"` 拼接（无尾随换行）：

```
template_id
sha256(lua 文件字节) 小写
parameter_schema_sha256 小写
approved_by
approved_at_utc
"lab01_passed=true|false"
"lab13_passed=true|false"
```
`registration_sha256 = sha256hex(UTF-8(canonical))`。**无任何密钥、盐、随机数混入。**

条目字段约束（`ParseRegistration` `:169-188`）：8 个字段恰恰好（多/少都拒）；`approved_by` ≤128 字符且无控制符；`approved_at_utc` 必须能被 `DateTimeOffset.TryParseExact("O")` 解析且偏移为 UTC（存量条目用 `…Z` 尾缀实测通过）；`lab01_passed`/`lab13_passed` 必须是 JSON 布尔 `true`（写成字符串 `"true"` 会报 `template_not_approved` 而不是 digest mismatch，`:186-187,342-347`）。

### 1.3 运行时校验顺序（每次 template.execute 现算，fail-closed）
`ApprovedTemplateRegistry.cs:45-107`，8 步：
1. template_id 合法性（`^[a-z0-9][a-z0-9._-]{0,79}$`，`:317-325`）
2. manifest.json 读取 + 与 manifest.sha256 对账（`template_manifest_digest_mismatch`，`:53-59`）
3. 条目查找唯一（`template_not_registered` / `template_registration_duplicate`，`:137-167`）
4. 请求参数 digest == 条目 sha256（`template_digest_not_registered`，`:66-67`）
5. **registration_sha256 复算对账（`template_registration_digest_mismatch`，`:69-78`）← 10-12 卡在这一关**
6. 磁盘 lua 现算 sha256 == 条目（`template_digest_mismatch`，`:80-84`）
7. 磁盘 schema 现算 sha256 == 条目（`:86-90`）+ schema 结构安全校验（仅标量、禁字段名，`:191-240`）
8. 参数 JSON schema 校验 + `ToolSecurityPolicy.TryAuthorize("template.execute")` 信封再授权（`:94-102`）

全部通过后返回不可变快照 `ApprovedTemplateExecution`；任何一步失败抛 `ApprovedTemplateException` 带错误码，Core 不被触碰。

## 2. 三个方案

每个方案末尾回答：**审批链的防滥用语义是否保持不变**（三道闸 = 目录写权限 + 人工仪式留痕 + 桥侧 fail-closed 校验）。

### 方案 A：登记工具便携化（推荐）

**做法**：把 LabConsole 里的登记工具打包为独立小工具包，在新机可用：
- 参数化 `register-m5-main.py` 的 `REG` 路径（`--registry` 参数，默认读 `<F1.exe目录>\WritableRoot.txt` + `templates\registry`），消除硬编码；
- 打包：register 脚本 + `lua_blacklist.py`（+tests）+ 新模板 lua/schema + 一份运行手册（dry-run → 安检 → owner `--apply` → 复算自检 → CLI 真机验证）；
- 新机登记流程与旧机逐字相同，审批仪式原样保留。

**利弊**：利——零编译、零部署窗口、当天可落地；威胁模型零变化（没有新增任何接口/程序面）；仪式与留痕是现成验证过的流程（4 条存量登记全部这样产生）。弊——仍是"跑脚本"的离线动作，不解决"面板一键"体验；每次登记要 owner 亲手敲 `--apply` 命令（这恰是审批本意）；公式公开后写权限是唯一硬闸（见 §0.4，需 owner 认知确认）。

**工作量**：≤1 人日（参数化 + 手册 + 新机验证），不占编译窗口。

**安全影响**：无新增攻击面。桥侧校验（§1.3）是唯一且充分的完整性保障，登记物进对目录即生效。

**防滥用语义**：**完全不变**。三道闸原样：谁写目录仍是文件系统权限；`--apply` 必带 `--approved-by/--approved-at` 留痕 + 安检前置；桥每次执行照旧现算校验。

### 方案 B：桥加正式注册接口

**做法**：在桥（F1.exe/AiAssistant）加登记端点或注册工具，审批参数（owner 令牌/审批口令）作为入参，把"审批"从离线工具变成显式运行时动作。需 C# 改动 + 重新编译 + 部署 F1.exe/F1.dll。

**利弊**：利——登记动作进审计流（桥审计已有基建 `BridgeAuditLogger`）、显式、可控（可用令牌+白名单+幂等）；新机零工具依赖。弊——①占编译/部署窗口（F1.exe/F1.dll 部署窗是稀缺资源）；②**违反既有设计声明**：`ApprovedTemplateRegistry.cs:13-14` 明写 "Registration stays outside the bridge"，动它属设计变更，需 owner 裁定；③威胁模型变体：闸的载体从"文件系统写权限"换成"桥令牌持有"——令牌泄漏 = 可登记，而今天写权限泄漏同样可登记，两者等价性需 owner 认可；④新端点即新攻击面（9477 目前只有 2 条路由，语义极简）。

**工作量**：3-5 人日 + 回归 + 部署窗口。若顺带做"owner 签名校验"（真密码学闸）另加 2-3 人日。

**安全影响**：新增 HTTP 面 + 令牌生命周期管理；若保持回环绑定 + token 鉴权 + 写前审批入参校验 + 审计，风险可控，但需要 owner 设计审批令牌的分发/轮换。

**防滥用语义**：**可保持，但载体换位**。①写权限闸从"人"变"持 token 的调用方"；②人工仪式必须保留（登记请求必带 approved_by/approved_at，且只能由 owner 审批界面发出）；③桥侧校验不变。语义等价性需 owner 拍板。

### 方案 C：登记代理服务（proxy 侧端点）

**做法**：在 proxy 加登记端点，owner 在面板/CLI 一键审批；proxy 收到审批后直接写四件套进 registry 目录 + 复算 manifest.sha256。桥零改动（校验在桥侧自然生效）。

**利弊**：利——最快落地，不占编译窗口（改 proxy 即可，与既有"digest 服务端 PIN"同侧）；体验最好（面板一键，面板基建已有工具通道+护栏）；写盘动作可进 proxy 审计。弊——①**proxy 服务端源码在本树未找到**（待 owner 提供），工作量只能估算；②"审批密钥怎么管"要先想清：**今日体系不存在任何密钥**——C 不应发明新密钥，正确做法是复用面板既有身份（面板登录/会话）+ 审批确认框 + 写前写后审计留痕；③proxy 代笔写文件后，"谁能写目录"等于"谁能过面板审批"，目录 ACL 应同步收紧到仅 proxy 运行账户，防绕过面板直接写盘。

**工作量**：proxy 代码 1-2 人日（待找到代码后核）；桥 0；面板一键审批 UI 另算。另需为新模板加结构化工具映射 + digest PIN（proxy 侧，不占编译窗口）。

**安全影响**：新增 proxy 端点（proxy 自身已是模型通道的咽喉，叠加登记功能要防模型误触：端点须 owner 会话独占，模型通道不可达）。写盘路径集中化后，registry 目录写权限收紧是配套动作。

**防滥用语义**：**可保持**。三道闸不变——写目录的手从 owner 直接操作变成"owner 在面板确认 → proxy 代笔"，但②人工仪式（审批确认框 + approved_by/approved_at 留痕）与③桥侧校验原样；①需配套 ACL 收紧。**前提**：不引入新密钥（今天没有密钥，别制造一个假密钥把体系变复杂）。
